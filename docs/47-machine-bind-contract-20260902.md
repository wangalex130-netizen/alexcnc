## 一、接口契约（权威）

### 3.1 设备绑定

```
POST /api/machine/bind?machineId=1&code=DEVICE-001
Authorization: Bearer {token}
```

| 参数 | 类型 | 必填 | 说明 | 位置 |
|---|---|---|---|---|
| `machineId` | long | ✅ | 机器 ID（t_machine 主键） | **Query Param** |
| `code` | string | ✅ | 机器码，最长 128 字符 | **Query Param** |

⚠️ **参数是 URL 查询串，不是 JSON body**。
实测：走 body（无论 `{code}` / `{code,machineId}` / `{machineCode}` / `{sn}` / `{}`）一律
**HTTP 500 `Internal Server Error`**，压根进不了业务逻辑；只有 query 传参才返回 HTTP 200。
两个参数**都必填**，缺任一个都是 500 或 `10300107`。

接口说明原文：
> 将机器码绑定到当前 Token 对应用户的一台机器。机器必须归属当前用户，
> 同一机器码只能绑定到一台机器。

响应示例：`{"code":200,"message":"10300106","data":1}`

### 3.2 设备解绑（App 暂未接入）

```
POST /api/machine/unbind?machineId=1
```
业务码：10300107 设备不属于当前用户 / 10300110 解绑成功 / 10300111 设备编码未绑定当前用户。

### 3.3 我的机器列表

```
GET /api/machine/list
Authorization: Bearer {token}
```
→ `{"code":200,"message":"10010101","data":[...]}`，**按机器 ID 倒序**返回。

## 三、🔴 产品语义（重要，需同步客服 / 销售侧）

**绑定 =「把机器码贴到账户下已有的机器档案上」。**

- 机器档案（`t_machine` 记录）**必须先由客服在后台录入到客户账户**，此时 `code` 为空。
- 客户拿到机器扫码 → App 找到账户里「还没贴码」的档案 → 把扫码所得的机器码贴上去。
- **光扫码绑不了新机器**：如果账户下没有空档案，扫码必然失败（提示"这台机器还没登记，请联系客服"）。

**⇒ 售前录入是扫码绑定上线的硬前提，需要同步给客服 / 销售侧。**
这也是合理的安全设计：防止客户扫别人的码把机器抢走。

## 四、App 实现（`machines_service.dart` / `bind_page.dart`）

1. 本地预检：空码 / 超 128 字符 → 直接提示，不发请求。
2. `GET /api/machine/list` 拿账户下档案。
3. 若已存在 `sn == 扫码值` 的机器 → **按成功直接返回**（对应 10300104 语义，重复扫不报错）。
4. 找 `code` 为空的档案（list 按 ID 倒序 → 取 `first` = 最新录入的那台）。
5. `POST /api/machine/bind?machineId=<档案id>&code=<扫码值>`（Query Param）。
6. 按上表映射业务码 → 抛 `BindFailure`（文案已 B2C 化，UI 直接展示）。
7. 成功后重新拉列表回填真实档案（`machineName` / `id`）。

**UI 侧（bind_page）**：
- 绑定前记录是否已选过机器；**若是账户里第一台，自动设为当前机器**（省客户再点一次）。
- 失败只展示 `BindFailure.message`，不再拼接技术异常文本。

## 五、实测验证记录（2026-09-02 闭环验证，已回滚）

数据污染修复后（381 恢复为空档案），用真实接口完整跑了一遍 App 的绑定流程，
验证完立即用 `unbind` 回滚，**最终状态与验证前完全一致**。

| # | 场景 | 请求 | 返回 | 结论 |
|---|---|---|---|---|
| A | 把**已被绑定的码**贴到空档案 | `bind?machineId=381&code=cnc-demo-01`（01 已被 375 占用） | `10300105` 设备编码已被绑定 | ✅ 映射到「这台机器已绑定其他账号」；**未改数据** |
| B | 贴**全新码**到空档案 | `bind?machineId=381&code=CNC-VERIFY-0902` | `10300106` 设备绑定成功 | ✅ 381 的 code 变为新码 |
| C | **重复贴同一个码** | 同上再调一次 | `10300104` 设备已绑定当前用户 | ✅ 与文档语义**一致**，按成功处理 |
| D | 回滚 | `unbind?machineId=381` | `10300110` 设备解绑成功 | ✅ 381 恢复空档案，其余三台原样 |

**⇒ 10300104 / 10300106 的语义本次实测与文档完全对上**（10300106=新贴码成功，
10300104=重复贴同一码）。此前观察到的"对不上"是首次调用时的边界表现，
建议 PC 工程师复核该分支；**App 已按"HTTP 200 且 biz code=200 = 成功"的稳妥写法实现，不依赖两者区分**。

### 已知后端行为（建议优化，低优先级）
- 空档案接受**任意格式**的机器码，连 `ZZZ-NOT-EXIST` 这类乱码也照收并写入。
  建议后端补机器码格式校验，避免扫到错码把档案写脏。
