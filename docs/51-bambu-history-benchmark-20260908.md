## 1. 核验后的事实（基于拓竹官方 Wiki / 隐私声明，2026-09-08）

| # | 事实 | 来源 |

| F1 | **Auto 模式（默认）**：切片文件先上传 Bambu 云，打印机从云下载；"也用于支持 Bambu Handy 的历史重打" | Bambu Wiki《Remote Control & Monitoring》 |

## 2. 纠正两项假设

- **假设 A"PC 切片 → LAN 直传机器"**：部分成立，但默认 **Auto 模式**下云端是**编排中枢 + 产物存储**，LAN 只是打印机的网络通路。关键见 F2：哪怕走 LAN 直传，云端仍会留一份 G-code 以支持历史重打。纯 LAN 模式（F6）才彻底不上云、无历史。
- **假设 B"电脑端只有历史无法重打"**：拓竹 PC 端（Bambu Studio）**实际支持**历史重打（F8）。你看到的"只有历史不能重打"最可能是：
  1. **G-code 已过 90 天保留期（F5）**——历史元数据留存、但可重打的产物已删 → 表现为"有记录、点不了重打"；或
  2. 你用的 PC 端看的是**本地工程历史**（.3mf 项目），而非云端 task 历史——两者不是一回事。
  → 这对我们的启示：**历史"能不能重打"取决于 G-code 产物是否还在**，而非历史条目本身。这是 `docs/50` 契约必须显式建模的点。

---

## 3. 为什么这么设计（why）

1. **手机无切片引擎** → 重打必须依赖"已切好的 G-code" → 该产物必须存在手机与打印机都能达的地方 → 只有云。所以"首次打印即上传 G-code 到云"是手机重打的前提（F1/F4）。
2. **统一真相源**：所有客户端（Studio/Handy/Web）、所有机器（多机 farm）的"打印过什么"只有云端一份，避免各端各存导致不一致。
3. **远程与连续性**：换手机/换网络/不在电脑前也能重打（生产复购场景）。
4. **审计/分析**：用量统计、故障追溯。
5. **生态粘性**：模型/历史沉淀在云，用户离不开。

## 4. 对我们的建议（修订 `docs/50` 契约）

| # | 修订 | 理由 |
|---|---|---|
| R1 | **坚持独立 `jobs` 表**（账号+机器ID 维度） | 拓竹验证"云为唯一真相源 + 统一 task 表"正确 |
| R2 | **PC 自生成刀路必须上传 G-code 到云并登记 `JobRecord`**（强化 §3.6） | 拓竹 F2 证明：即便 LAN 直传也上传云；我们 PC 自生成路径绝不能"纯局域下发不留云"，否则统一历史漏记 |
| R3 | **新增 `gcodeExpiresAt` 字段 + 重跑态 `rerunable/expired`** | 解释"有历史不能重打"=G-code 过期（F5）；CNC G-code 体积大且有 IP，保留策略需用户可控，列表应显式标"已过期不可重跑" |
| R4 | **新增 `storeGcode` 标志（隐私，对标 F6 LAN/Incognito）** | Pro/Max 小B 可能有专有零件刀路，应允许"不存云端 G-code、仅存元数据或本地留"；B2C 海外默认存 |
| R5 | **重跑接口强制 `materialReconfirm` 参数（CNC 安全，差异化改进）** | 3D 打印一键重打低风险（换料打印机可检）；CNC 刀路硬编码转速/进给/深度/材质，换料换刀有断刀/废件风险 → 重跑前须材质+刀具复核（至少确认弹窗），不能像拓竹一键重打 |
| R6 | **App 与 PC 双端均可从云历史重跑** | 拓竹 Studio+Handy 都能重打（F8）；我们 PC 也是控制面，应放开 |
| R7 | **账号/区域隔离沿用现有三层架构** | 拓竹 F7 区域账号分离；我们海外(HK EMQX)+国内已分层，历史须随账号区域边界 |
