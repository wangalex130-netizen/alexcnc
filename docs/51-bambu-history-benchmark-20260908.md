## 2. 纠正两项假设

- **假设 A"PC 切片 → LAN 直传机器"**：部分成立，但默认 **Auto 模式**下云端是**编排中枢 + 产物存储**，LAN 只是打印机的网络通路。关键见 F2：哪怕走 LAN 直传，云端仍会留一份 G-code 以支持历史重打。纯 LAN 模式（F6）才彻底不上云、无历史。
- **假设 B"电脑端只有历史无法重打"**：你的截图 S1 **坐实**了这一点——Bambu Studio 的该详情页确实没有重打按钮。PC 端并非不能重打，而是：
  1. **PC 端有源文件/切片工程**（.3mf），可以直接从源文件「切片 → 打印」，不需要依赖云端 G-code，因此 UI 上不必在历史详情里放「重新打印」；
  2. **App 端没有切片引擎**，只能从云端取已切好的 G-code，所以必须在历史详情里提供「重新打印」。
  → 这对我们的启示：**历史"能不能重打"取决于客户端是否有能力重新生成/重新获取 G-code**。PC 端靠本地工程，App 端靠云端 G-code。`docs/50` 契约必须显式区分「源文件（PC 本地可重跑）」与「云端 G-code（App 重跑所需）」。

---

## 3. 为什么这么设计（why）

1. **App/手机无切片引擎** → 重打必须依赖"已切好的 G-code" → 该产物必须存在手机与打印机都能达的地方 → 只有云。所以"首次打印即上传 G-code 到云"是 App 能重打的前提（F1/F4）。
2. **PC 有切片引擎 + 本地工程文件** → 可以直接从 .3mf 工程重新切片打印，不需要依赖云端历史里的 G-code。所以 PC 端历史详情页不放「重新打印」也成立（F8/S1）。
3. **统一真相源**：所有客户端、所有机器（多机 farm）的"打印过什么"的**元数据**只有云端一份，避免各端各存导致不一致。
4. **远程与连续性**：换手机/换网络/不在电脑前也能重打（生产复购场景）。
5. **审计/分析**：用量统计、故障追溯。
6. **生态粘性**：模型/历史沉淀在云，用户离不开。

## 4. 对我们的建议（修订 `docs/50` 契约）

| # | 修订 | 理由 |
|---|---|---|
| R1 | **坚持独立 `jobs` 表**（账号+机器ID 维度） | 拓竹验证"云为唯一真相源 + 统一 task 表"正确 |
| R2 | **PC 自生成刀路必须上传 G-code 到云并登记 `JobRecord`**（强化 §3.6） | 拓竹 F2 证明：即便 LAN 直传也上传云；我们 PC 自生成路径绝不能"纯局域下发不留云"，否则统一历史漏记 |
| R3 | **新增 `gcodeExpiresAt` 字段 + 重跑态 `rerunable/expired`** | 解释"有历史不能重打"=G-code 过期（F5）；CNC G-code 体积大且有 IP，保留策略需用户可控，列表应显式标"已过期不可重跑" |
| R4 | **新增 `storeGcode` 标志（隐私，对标 F6 LAN/Incognito）** | Pro/Max 小B 可能有专有零件刀路，应允许"不存云端 G-code、仅存元数据或本地留"；B2C 海外默认存 |
| R5 | **重跑接口强制 `materialReconfirm` 参数（CNC 安全，差异化改进）** | 3D 打印一键重打低风险（换料打印机可检）；CNC 刀路硬编码转速/进给/深度/材质，换料换刀有断刀/废件风险 → 重跑前须材质+刀具复核（至少确认弹窗），不能像拓竹一键重打 |
| R6 | **App 端必须能从云历史重跑；PC 端至少可查看完整历史，重打能力视场景而定** | 拓竹 PC 因本地有切片/工程文件，历史详情不放重打；我们 PC 若也有 CAM/源文件能力，可只保留「查看」+「打开源工程」，不强制重打。但统一 `jobs` 表仍需记录 PC 发起的每一次执行（R2）。 |
| R7 | **账号/区域隔离沿用现有三层架构** | 拓竹 F7 区域账号分离；我们海外(HK EMQX)+国内已分层，历史须随账号区域边界 |
