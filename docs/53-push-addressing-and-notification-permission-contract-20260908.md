# 53 推送寻址与通知权限契约

> 日期：2026-09-08　状态：**已拍板，供后端 / App / PC 三端实现**
> 目标：**该收的收到，不该收的不收到**
> 关联：`47-machine-bind-contract`（绑定关系唯一数据源）、`44-project-ledger`（项目台账）

---

## 1. 核心结论（先看这一节）

1. **个推只做通道，"谁该收"由云端决定。**
   个推只知道「把消息送到某个 alias 绑定的所有设备」，它不知道机器、不知道绑定关系。
   所有权限判断必须在云端完成。

2. **寻址主键是 `accountId`（alias = userId），不是 CID。**
   CID 是「设备 × App × 安装级」标识，**重装 App 会变**（2026-09-08 真机实测证实）。
   拿 CID 当业务标识会导致重装用户永久失联。

3. **绑定关系唯一数据源 = 云端 binding 表**（定义见 `47-machine-bind-contract`）。
   只要绑定表改了，通知行为立刻跟着变，**不需要动个推任何配置**。

---

## 2. 已确认的产品决策（2026-09-08 拍板）

| # | 议题 | 决策 |
|---|---|---|
| 1 | 单账号多设备（手机 + 平板） | **都收**。已读状态云端同步，避免多处红点 |
| 2 | 小B 多账号共用一台机器 | **本期不支持**。一台机器同一时刻只能绑定一个 `accountId` |
| 3 | 机器转让 / 解绑 | **原账号有权解绑**。转让后**旧主人的历史数据清空** |

> 决策 2 的直接收益：寻址逻辑大幅简化——「这台机器绑了谁」的答案恒为 0 或 1 个账号，
> 不需要角色系统、不需要按角色过滤。**若未来要支持小B 共用，需新增角色模型并回头扩展第 4 节。**

---

## 3. 寻址决策链（四层过滤，全部在云端）

```
[1] 事件源        机器/云端产生事件（雕刻完成、告警、断刀…）
      ↓
[2] 绑定关系      查 binding 表：这台 deviceId 绑了哪个 accountId？      ← 本期答案恒为 0/1 个
      ↓
[3] 类型与角色    这类通知，该账号有没有权限收？                          ← 本期单账号即管理员
      ↓
[4] 偏好开关      用户自己在 App 里关掉的类型不再下发
      ↓
[5] 得出目标 accountId 列表
      ↓
[6] 个推按 alias=accountId 推送（自动展开到该账号所有设备）
```

**关键**：第 2~4 层全在云端。个推侧永远只有 `alias = userId` 这一个概念，
不建 tag、不建机器维度的别名——否则绑��关系一变就要同步个推配置，迟早不一致。

---

## 4. 场景矩阵与期望行为

### 4.1 账号 ↔ 设备

| 场景 | 期望行为 | 实现要点 |
|---|---|---|
| 单账号单设备 | 正常收到 | — |
| **单账号多设备** | **都收到** | 个推 alias 天然支持「一个 alias 绑多个 CID」；已读状态云端同步 |
| **同设备切换账号** | **只收当前账号的** | 切换时先 `unbindAlias(旧)` 再 `bindAlias(新)`，**顺序不能反** |
| 未登录 | 不收任何业务通知 | 未 bindAlias，云端无从寻址 |
| 账号注销 / 被禁用 | 立刻不再收 | 云端注销流程必须包含 unbind + 清绑定表 |

### 4.2 账号 ↔ 机器

| 场景 | 期望行为 |
|---|---|
| 一个账号绑多台机器 | 都收，消息体带 `deviceId` + 机器名以便区分 |
| 新机器绑定成功 | 立即可收（无需改个推配置，符合「五闸门模型」） |
| **机器解绑 / 转让** | **旧主人立刻不再收**；其历史数据清空 |
| 机器被解绑后重新绑定新账号 | 新账号立即可收，与旧账号完全隔离 |

### 4.3 通知类型 × 接收者

> 本期「一台机器 = 一个账号」，所以接收者恒为该机器绑定账号，**角色维度暂不生效**。
> 下表为未来扩展小B 角色时的预留，本期实现可先按「全部发给绑定账号」处理。

| 类型 | 本期接收者 | 未来（小B 角色化后） |
|---|---|---|
| 雕刻完成 / 失败 | 绑定账号 | 发起人 + 管理员 |
| 断刀检测 / 加工异常 | 绑定账号 | 当前操作者 + 管理员 |
| 机器离线 / 上线 | 绑定账号 | 管理员 |
| 固件可升级 | 绑定账号 | 管理员 |
| 账号安全类 | 该账号**所有**设备 | 同左 |
| 系统公告 / 运营 | 全量 | 同左 |

## 5. CID 生命周期（App 端强制要求）

这是「该收没收到」类故障的高发区，**必须严格按此实现**：

| 时机 | 动作 |
|---|---|
| 首次启动 + 同意隐私政策 | 初始化个推 → 拿到 CID → `bindAlias(userId)` |
| **重装 App** | CID 已变 → 启动后**必须重新** `bindAlias(userId)` |
| **切换账号** | 先 `unbindAlias(旧userId)` → 再 `bindAlias(新userId)` |
| **登出** | `unbindAlias(userId)` |
| 账号注销 | `unbindAlias(userId)` + 云端清绑定表 |

> ⚠️ 「切换账号」若漏掉 unbind，会出现**新用户看到上一个账号机器通知**的串号事故，
> 属于隐私红线，必须在 Code Review 中重点检查。

---

## 6. 高危漏洞清单与防护

### 6.1 「不该收却收到」（隐私事故，优先级最高）

| # | 漏洞 | 防护 |
|---|---|---|
| 1 | **换账号没 unbind** → 串号 | 第 5 节切换流程强制 unbind |
| 2 | **机器转让后旧主人仍在绑定表** | 解绑接口必须**同步**删 binding 记录 |
| 3 | 员工离职未解绑 | 账号注销流程包含清绑定（复用 #2） |
| 4 | App 卸载但 alias 未解绑 | 卸载无法感知，靠「离线超过 N 天自动清理 alias」兜底 |
| 5 | 账号注销后 alias 残留 | 注销流程 = unbind + 清表 + 清历史（决策 3） |

### 6.2 「该收却没收到」

| # | 漏洞 | 防护 | 备注 |
|---|---|---|---|
| 1 | **重装后 CID 变，未重新 bind** | 启动后无条件 `bindAlias` | 2026-09-08 实测证实 |
| 2 | **init 后约 48 秒长连接握手期** | 期间推送进离线队列，属正常 | 实测：T+48s 才 `successed_online` |
| 3 | **App 退后台被系统杀掉** | 需厂商离线通道（**需上架应用商店**） | 自分发 APK 无法规避 |
| 4 | 离线消息过期后补推造成打扰 | 设离线有效期（建议 24h），过期不补 | 避免「三小时前的雕刻完成」 |
| 5 | **通知运行时权限未申请** | App 主动申请 `POST_NOTIFICATIONS` | Android 13+ / 鸿蒙强制 |

## 7. 客户端（App）实现要求

1. **前台必须自己弹通知**：个推 SDK 在 App 前台**不会**自动弹系统通知栏，
   而是走 `onNotificationMessageArrived` 回调交给 App。该回调**不得为空实现**，
   需调用本地通知展示（本项目用 `flutter_local_notifications`）。
2. **必须申请通知运行时权限**：`Android 13+ / API 33+` 的 `POST_NOTIFICATIONS` 是运行时权限，
   仅在 manifest 声明无效。
3. **已读状态云端同步**：单账号多设备都收，需在云端维护已读水位，避免多设备红点不一致。
4. **推送文案敏感词**：文案中**不得出现「个推」二字**，会被服务端拦截（实测）。

## 9. 本期边界（明确不做）

- ❌ 多账号共用一台机器（决策 2）
- ❌ 角色系统（管理员 / 操作员）
- ❌ 按机器维度的个推 tag 寻址（一律走云端）
- ❌ 消息撤回 / 已读回执以外的复杂状态机

---

## 10. 三端分工

| 端 | 职责 |
|---|---|
| **云端（阿里云 API）** | 维护 binding 表；实现第 3 节四层过滤；调用个推 REST API 下发 |
| **App（Flutter）** | CID 生命周期管理（第 5 节）；本地通知展示；权限申请；偏好开关 UI |
| **PC / 固件** | 产生事件时**只上报状态**，不参与寻址决策 |

> 事件上报方（PC / 固件）**禁止**自行判断"该发给谁"——寻址决策权 100% 在云端。
