# 三终端 × 双云服务器：功能与交互梳理（总纲）

> 目的：把「机身屏（机器终端） / 手机 App / 电脑端应用（ArtiMaker）」三终端，与
> 「视频推流服务器 / 状态控制+模型库服务器」双云端之间的**全部功能、交互、发送/接收内容、
> 优先级、内网/外网边界**梳理清楚，作为三端与云端团队并行开发的对齐基线。
> 配套：`docs/PROTOCOL.md`（帧/报文契约）、`docs/STEP1-LAN-实施设计.md`（第一步落地）、
> `docs/功能逻辑与分工梳理.md`（App 内部全景）。

---

## 0. 结论速览（先读这段）

1. **「机器终端（机身屏）」是系统核心**：ESP32 是状态唯一真值源（SSOT），机身屏是机器侧
   唯一的本地人机界面（状态/报警/配对码/基础控制）；App 与电脑端都是它的**远程镜像与扩展**。
2. **双云端假设成立，职责如下**：
   - **视频推流服务器**：接收机器/摄像头推流（RTMP/WebRTC），向外网三端分发（HLS/WebRTC）；
     内网时三端直连 RTSP，不经过它。
   - **状态控制+模型库服务器**：设备注册/在线、状态汇聚、命令转发（外网）、模型/G-code 库、
     任务元数据、材质参数主表、账户与历史、诊断。**它是三端同步的中枢**。
3. **App ↔ 电脑端不直连**；二者统一经「状态控制服务器」同步（模型库/任务/历史/材质），
   内网控制与视频则各自直连机器。内网断外网时，用**局域网伴随服务**（`server.py` 演进）兜底。
4. **落地顺序**：内网直连闭环（第一步）→ 外网 MQTT+视频推流（第二步）→ 三端深度同步（第三步）。

## 2. 三终端定位与职责

| 端 | 角色定位 | 核心职责 | 真值源依赖 |
|----|---------|---------|-----------|
| **机身屏（机器终端）** | **系统核心 / 机器侧 HMI** | 实时显示状态/坐标/进度/报警；配网与配对码展示；基础控制（暂停/急停/回零）；断网兜底操作 | ESP32（同机共享，不走网络） |
| **手机 App（alexcnc）** | 移动控制端 / 移动监控端 | 模型库浏览→向导 6 步→控制；实时监控（状态+RTSP+2D 刀路）；远程监视（外网）；配网助手 | 状态来自 ESP32/服务器，本地只渲染 |
| **电脑端（ArtiMaker）** | 设计/切片工作站 + 控制端 | 🎨设计（资源库/AI/2D·2.5D）→ ⚙️生成（一键刀路/3D 预览）→ 🔨制作（控制/GRBL 兼容）；模型与任务产出端 | 切片与设计本地完成；控制与状态来自机器 |

> **为什么机身屏是核心**：即使 App/电脑端全部离线，机器仍能独立运行——自检、加工、报警、
> 急停都由 ESP32 本地闭环；机身屏是这台"本地闭环"的人机出口。三端只是对同一真值的不同镜像。

## 3. 双云端服务器职责（确认你的假设 ✅，并细化）

### ① 视频推流服务器（媒体面）
| 能力 | 说明 |
|------|------|
| 收流 | 机器端把 RTSP 转推上来（RTMP / WebRTC / SRT） |
| 分发 | 外网三端经 HLS（低延迟档）/ WebRTC（实时档）观看；内网不经过它（直连 RTSP） |
| 地址注册 | 推流地址/播放地址上报给②，由②分发给各端 |
| 录播（可选 P2） | 延时摄影、加工回放存档 |

### ② 状态控制 + 模型库服务器（业务面，三端同步中枢）
| 域 | 能力 |
|----|------|
| 设备 | 注册/认证（Token）、在线状态、配网/配对码校验、固件版本 |
| 状态 | 汇聚机器 statusStream（外网中转给三端）、报警告警推送 |
| 命令 | 外网控制转发（App/电脑端 → 机器），限权（监视模式锁 Jog/开切） |
| 模型库 | 灵感库（公开）、我的空间、历史记录；模型/图纸资产 |
| 任务/G-code | 切片服务、TaskMetadata（尺寸/材质/刀具）、**G-code 直推机器**（App/电脑端不持有） |
| 材质 | 材质参数主表（rpm/feed/plunge/刀具），三端共用 + 本地缓存 |
| 账户 | 登录/注册、设备绑定、跨端会话 |
| 诊断 | 日志上报、远程排障 |

> **②与①的交互**：机器推流成功后把「播放地址」上报② → ②把地址写入设备详情 → 三端从②
> 拉取播放地址后连①观看。①本身不存业务数据。

## 6. 内网 / 外网 边界细则

| 维度 | 内网（同 Wi-Fi） | 外网（4G/异地） |
|------|----------------|----------------|
| 控制 | 直连机器 TCP:8899，低延迟全功能（Jog/回零/开切） | 经② MQTT 转发，**监视模式**（锁 Jog/开切，仅监控+暂停/停止） |
| 状态 | 直连订阅 5–10Hz | 经② 汇聚 1–5Hz |
| 视频 | 直连 RTSP（200–500ms 延迟） | 经① WebRTC/HLS |
| 模型库/任务/材质/账号 | 经②（或局域网伴随服务兜底） | 经② |
| G-code | 局域网伴随服务/② 直推机器 | ② 直推机器 |
| 断外网 | 完整可用（控制+状态+RTSP+局域网服务） | 不可用（依赖云端） |
| 判定 | mDNS 能发现机器 或 手动同网段 | mDNS 扫不到 → 走云端 |

> **切换逻辑**：App/电脑端启动 → mDNS 探测 → 同网段则走直连（全功能），否则走②（监视模式）。

## 7. 内网「电脑端 / App 同步」专项（你点名的痛点）

### 7.1 需要同步什么

| 数据 | 真值源 | 流向 | 何时同步 |
|------|--------|------|---------|
| 模型/任务（电脑端设计产物） | 电脑端（ArtiMaker）→② | 电脑端→②→App 图库 | 电脑端生成时上传；App 拉取（启动/下拉刷新/推送） |
| 任务元数据（尺寸/材质/刀具/预览矢量） | ②（切片后回填） | ②→三端 | 任务就绪时 |
| G-code | ②/局域网服务 | **直推机器**，三端不持有 | startJob 前 |
| 材质参数/刀库 | ②（主表） | ②→三端缓存 | 启动 + 打开页面静默刷新 |
| 历史记录/我的空间 | ② | ②→App/电脑端 | 进入页面/刷新 |
| 机器状态 | ESP32 | 各自直连（内网）或经②（外网） | 实时 |

### 7.2 同步方案选项（需你拍板）

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A 纯云端中枢（推荐起步）** | 电脑端/App 全部经②同步；内网控制仍直连机器 | 实现最简单，一套逻辑贯穿内外网；与账号绑定 | 断外网时模型库/任务同步不可用（控制不受影响） |
| **B 局域网伴随服务** | 内网多跑一个 `server.py` 类服务：模型库+G-code 中转 | 断外网也能完整设计→下发→加工 | 需部署/维护一台局域网服务器；与②数据双写 |
| **C 混合（最终形态）** | 内网优先局域网服务，外网走②，二者数据最终一致 | 体验最好、可用性最高 | 要处理"双写冲突/最终一致"，复杂度高 |

**建议**：先按 **A** 落地（与 Step1/Step2 顺序一致），B 作为断网增强（`server.py` 已具备雏形），
C 等三端功能稳定后再评估。

### 7.3 明确"不直连"的交互（避免重复建设）

- App 与电脑端**不做点对点文件传输**：模型/G-code 要么经②、要么经局域网服务，单一来源。
- 三端**不做状态互转**：都订阅 ESP32 同一真值，谁在线谁显示，不互相代传。
