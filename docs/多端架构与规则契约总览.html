§0 多端拓扑图（双云部署）

五端角色：手机 App（控制/监控）、ESP32-S3 固件（执行）、腾讯云（MQTT Broker + 视频流）、阿里云 037123.xyz（REST API + DB + G-code 文件服务）、摄像头（独立 RTSP 上行）。关键澄清：MQTT 与视频流在腾讯云同一台；API 与 DB 与 G-code 文件服务在阿里云 037123.xyz 另一台；阿里云以常驻客户端 bridge-aliyun 跨连云 broker（见 §18）。

双云结论（工程师 2026-08-13 补充，已写入契约）：
  • 视频流服务 + MQTT Broker = 腾讯云同一台（MQTT 主链路在此）。
  • 三端 REST API + 数据库 + G-code 文件服务 = 阿里云 037123.xyz 另一台（设备绑定、刀库更新、模型库、任务、G-code 文件服务均在此，Q3 已定）。
  • App 与固件都跨云双连：App → 阿里云(REST) + 腾讯云(MQTT/视频)；固件 → 腾讯云(MQTT) + 阿里云(G-code 下载)。
  • 阿里云以常驻客户端 bridge-aliyun 跨连云 broker，单一通道承载 ACL 同步 / job prepare / tool_catalog 广播（Q1 已定，不建 broker REST admin 面）。

§1 一句话流程

App UI ──调用──▶ HardwareService / CloudService（抽象接口）
                        │
        三方实现 ────────┤  RealHardwareService  （App ↔ 机器：LAN TCP:8899 / WAN MQTT↔腾讯云）
                        └  RealCloudService     （App ↔ 阿里云 REST：模型库/任务/设备/刀库）

机器 = ESP32-S3 屏幕（MQTT clientId = screen-<deviceId>）+ 板载 GRBL（UART 直控）。无 STM32F407 主控；如未来 407 独立联网，仅作为 bridge-<deviceId> 预留身份。

§2 三大设计原则

① 机器是唯一真值源（SSOT，运行时）

  • App 不裁决坐标、刀仓在位状态、加工状态；只监听机器广播并渲染。
  • 所有 MachineStatus 由 MCU 产生。注意：刀库目录(catalog)是云资产（见 §17），不在此原则内。

② 资产闭环：手机绝不持有 G-code

  • 切片文件由阿里云经 LAN / MQTT 直接下推 MCU。
  • App 只取 TaskMetadata 与极小 2D 矢量渲染 JSON。

③ LAN / WAN 鉴权

  • 同 Wi-Fi → isLocalLAN=true（全功能）。
  • 公网 / 腾讯云 MQTT → false（监视：监控 + pause/resume/stop + light/fan + OTA）。

§4 传输层

4.1 局域网（LAN）—— TCP:8899 直连

  • 端口固定 8899。机器开 TCP Server，App 作 Client 直连 机器IP:8899，长连接双向收发，换行分隔 JSON 帧。
  • 不依赖 Broker / 云端 / 外网。mDNS：alexcnc-<sn>.local（port 8899）。

4.2 外网（WAN）—— 腾讯云 MQTT Broker

  • 主链路：腾讯云 MQTT Broker，生产 8883 TLS，关匿名，私有域名；联调 1883。WebSocket 统一 8083。

§8 状态机

disconnected idle homing busy paused alarm

idle ──home()──▶ homing ──▶ idle
idle ──job prepare──▶ download ──▶ ready ──startJob──▶ awaitingConfirm ──物理确认──▶ busy
busy ──pauseJob()──▶ paused ──resumeJob()──▶ busy
busy/paused ──stopJob()──▶ idle
busy ──(异常)──▶ alarm ──(复位)──▶ idle
任意 ──disconnect()──▶ disconnected
  • ready/awaitingConfirm 是标志位，非独立枚举。
  • 自检非独立态：busy + scIndex/scTotal。

8.1 自检 5 阶段（固件拥有）

  • ① pp_matched ② pp_lev ③ pp_tool ④ pp_warm ⑤ pp_all；时序 [1100,3300,1600,1800,900] ms ≈ 8.7s。
  • App 只渲染，不计时。

§9 G-code 下发链路

不变式：App 永不持有 G-code。真实切片文件由阿里云经 LAN / 腾讯云 MQTT 直推 MCU（Q3 已定：文件服务统一阿里云）。
① 电脑端/阿里云把 G-code 存到阿里云文件服务 → 预签名 URL（同云 037123.xyz）
② 阿里云 API：POST /api/v1/devices/{id}/jobs（job prepare，含 gcodeUrl + compensation）
   → 阿里云以 bridge-aliyun 身份向腾讯云 broker 发 cnc/{id}/cmd：{"cmd":"job","action":"prepare","gcodeUrl":...}
③ 机器 HTTP 异步下载(→阿里云文件服务，device token 鉴权) → 广播 download 进度 → state=ready
④ startJob → awaitingConfirm=true → 机身屏「确认加工」
⑤ 机旁物理键确认 → 自检(sc 0→5) → 加工(progress/eta) → idle
  • compensation：任务属性（host/firmware），每任务仅一个补偿方。
  • gcode 帧保留为小文件调试通道。

§10 设备注册与绑定

  • deviceId == serial == 机器唯一码，三文档统一用作 MQTT 主题隔离与账号绑定依据。
  • 连接层：机器连接后发 hello 命令帧上报机型与唯一码。
  • 授权层（跨云）：阿里云 API 的「设备绑定」接口是绑定权威源——用户注册账户 → 扫码/输入唯一码 → API 建「账号↔机器」绑定 → API 以 bridge-aliyun 客户端经 cnc/sys/acl 向腾讯云 broker 同步 ACL，使该 app-<userId> 可发布/订阅对应 cnc/<deviceId>/*（Q4 已定重试/对账机制）。
  • 一账号可挂多台，当前单机连接（切换即断开上一台）。

13.4 阿里云 API 服务器侧

  • G-code 文件服务（Q3 已定）：存储/服务/编排全在阿里云，提供预签名 URL 供固件 HTTPS 下载。

16.2 跨云集成点（已拍板）

阿里云 API 服务器 ≠ 纯 REST 服务，它必须也是腾讯云 broker 的 MQTT 客户端。
  1. 设备绑定的 ACL 落地：用户在阿里云绑定设备后，broker（腾讯云）并不知道该账号有权访问哪个 cnc/<deviceId>。由阿里云 API 的 bridge-aliyun 客户端经 cnc/sys/acl 把绑定关系写进 broker ACL（Q1/Q4 已定）。
  2. 服务端发起的命令：§9 的 job prepare 由阿里云 API 触发，但真正下发给固件要走腾讯云 broker 的 cnc/<deviceId>/cmd。阿里云 API 以 bridge-aliyun 身份 publish（Q1 已定）。
  3. G-code 文件服务位置：与阿里云 API 同云（同域/同 OSS，Q3 已定），固件 HTTP 下载走阿里云；视频流在腾讯云。两条大流量分开，互不挤占。
  • 网络策略：固件需能出公网访问① 腾讯云 8883（MQTT）② 阿里云 HTTPS/文件服务（G-code）；阿里云 API 需能出公网访问腾讯云 8883（broker admin）。防火墙需放开这三组。

17.2 设备绑定接口 → 与 §10 的关系

结论：无冲突，互补。
  • 阿里云「设备绑定」接口 = 绑定的唯一权威源（写 DB）。它决定「哪个 userId 拥有哪台 deviceId」。
  • 固件 hello 命令帧 = 连接层身份声明（「我是 serial=XXX 上线了」），不是授权。
  • 腾讯云 broker ACL = 运行的授权，由阿里云绑定事件经 bridge-aliyun 驱动写入（跨云 cnc/sys/acl 同步）。没有这步，固件发了 hello 也连不上主题、App 也订阅不到。

落地要求：阿里云绑定接口在「创建/解除绑定」事务提交后，必须异步调用 broker ACL 同步（成功/失败可观测，失败按 Q4 重试）。这是双云架构下最容易漏的一环。

17.3 刀库更新接口 → 双 ownership 澄清（Q2 已拍板）

工程师说 API 已有「刀库更新」，而契约 §6 又有 App→固件 toolMap 命令。二者不是同一件事，必须拆清：

已拍板分工（2026-08-14，Q2 = 否）：
  • 刀库更新 REST = 只管目录持久化（DB 里有哪些刀、参数怎么改）→ 落库后广播 tool_catalog。
  • toolMap 命令 = 只管运行时应用（把目录里的某几把刀指派到本机卡槽）。由 App 在向导 Step3 / 控制台发起，实时下发给固件。
  • 阿里云 API 绝不发 toolMap 给固件——否则会出现「REST 改了目录、API 又推了 map、App 又推了 map」三写冲突。固件侧 toolMap 的唯一入口保持为 MQTT 命令。

App 侧现状：本地 tool_library.dart 是目录的离线副本/缓存（已锁 5 把官方 3.175 刀），真正的目录以阿里云 DB 为准；换网络/换账号时从 tool_catalog 广播或 刀库更新 接口拉取刷新。

17.4 其它接口归位

  • /devices/{id}/jobs = §9 的 job prepare 触发入口；其内部应转为「阿里云→腾讯云 broker 以 bridge-aliyun 下发 cnc/{id}/cmd job prepare」，而非直连固件（Q1）。
  • /materials = 材料库，与之前 Excel「刀具-材料-参数」关联分析对接（材料级默认参数，推荐刀具按类型推导）。
  • /diagnostics = 运维健康，建议也走 broker cnc/{id}/log 或 notify 补充实时性。

§18 四项跨云决策（2026-08-14 由 App 任务拍板，四方执行）

原 §17.5 四个待拍板项，已由 App 任务在 2026-08-14 统一拍板。以下为逐条决策、理由与四方影响，可直接转阿里云 API / 腾讯云 MQTT / 固件 / App 四方执行。

Q1 阿里云 ↔ Broker 连接方式：常驻 bridge 持久客户端（单一通道）

拍板：bridge-aliyun 常驻客户端
  • 阿里云 API 服务器以持久 MQTT 客户端身份 bridge-aliyun（TLS 8883，私有证书）常连腾讯云 broker。
  • 该客户端统一承载三类跨云下发：① 设备绑定/解绑 → ACL 同步控制消息；② job prepare 等命令 → cnc/<deviceId>/cmd；③ 刀库目录更新 → cnc/<deviceId>/tool_catalog（retain）。
  • 不引入 broker REST admin 面：ACL 同步通过 bridge-aliyun 发布控制消息到特权主题 cnc/sys/acl，由 broker 认证后端消费并应用，避免双通道维护。
  • 收益：pub/sub 语义统一、QoS/retain 可控、阿里云侧只维护一个长连接。
四方影响：① 阿里云 API 实现 bridge-aliyun 长连接；② 腾讯云 MQTT 提供 cnc/sys/acl 入口 + 认证后端消费；③ 固件无感（仍只认 bridge-aliyun 发的 cmd/tool_catalog）；④ App 无感。

Q2 刀库更新是否推 toolMap：否

拍板：否（仅 tool_catalog 广播）
  • 刀库目录（catalog）更新 → 只广播 cnc/<deviceId>/tool_catalog（retain=true）。
  • 绝不推送 toolMap。toolMap 严格是机器运行时命令，由操作员/App 在 W4 步骤下发，机器拥有。
  • 理由：目录是云资产、ToolMap 是机器运行时真值，语义不同；禁止阿里云推 toolMap 可杜绝「REST 改目录 + API 推 map + App 推 map」三写冲突。
四方影响：① 阿里云 API 刀库更新只写 DB + 广播 catalog；② 腾讯云 MQTT 保留 tool_catalog 广播通道；③ 固件订阅 tool_catalog 刷新本地目录缓存（派生、不回写）；④ App 订阅 tool_catalog 刷新本地刀库（已锁 5 把官方刀）。

Q3 G-code 文件服务位置：统一阿里云

拍板：统一阿里云 037123.xyz
  • G-code 文件存储 / 服务 / 「push to MCU」编排全部落在阿里云（与 API/DB 同云）。
  • 字节传输：机器经 HTTPS 从阿里云下载（device token 鉴权）；broker 仅承载 job 命令 + G-code URL（不传字节），与「App 绝不持有 G-code」资产闭环一致。
  • 腾讯云保持无状态：仅 broker + 视频流。
四方影响：① 阿里云 API 提供预签名 URL；② 腾讯云 MQTT 不碰 G-code 字节；③ 固件 G-code 下载改走阿里云 HTTPS；④ App 不持 G-code（不变）。

Q4 ACL 同步失败重试策略（至少一次 + 幂等 + 持久补偿 + 重连重放 + 周期对账）

拍板：幂等队列 + 指数退避 + 三重重投 + 降级
  • 幂等键：每个绑定/解绑事件生成 aclOpId（复用绑定记录 id），重试安全、不重复授权。
  • 持久队列：阿里云 DB 存 acl_sync 表，状态 pending→acked→failed，含 opId / 目标 machineCode / accountId / payload / retryCount / nextRetryAt。
  • 指数退避：1s→5s→30s→2min→10min→1h，最多 8 次；耗尽标 failed 并告警（向运维/账号推 notify）。
  • 三重重投：① 失败立即排程；② bridge-aliyun 重连成功时重放所有 pending；③ 每 5min 全量对账（DB 绑定 vs broker ACL 实际态），修复漂移。
  • 成功判据：broker 认证后端处理控制消息后回 ACK（bridge-aliyun 收 cnc/sys/acl/ack）；5s 超时无 ACK 视为失败重试。
  • 可见性：绑定页展示同步态（同步中 / 已生效 / 失败），失败不让用户误判绑定成功。
  • 降级：broker 长期不可达 → 绑定仍写 DB 成功（业务可用），ACL 未生效；broker 恢复后由重连重放自动补；页面提示「网络恢复后将自动授权」。
四方影响：① 阿里云 API 落 acl_sync 队列 + 重试；② 腾讯云 MQTT 提供 cnc/sys/acl/ack 回执；③ 固件无感；④ App 绑定页展示同步态。
