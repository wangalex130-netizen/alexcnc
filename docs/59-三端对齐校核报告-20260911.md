## 一、执行摘要

**一句话**：三端"能跑通"的部分其实对得不错，但**安全边界（谁拦外网命令）出现责任真空，且三端各自拿着一份不同的契约**——这是所有不一致的总根源。

**最严重的三件事（P0）**

| # | 问题 | 后果 |
|---|---|---|
| **P0-1** | **外网命令拦截责任真空**：固件把 `is_wan` 硬编码为 `false`（注释称"云网关会拦"），而后端**根本没有命令白名单逻辑** | 任何人拿到 broker 凭据，**从外网就能让机器点动/回零/启动雕刻**（落刀、撞刀、火灾风险） |
| **P0-2** | 固件 WAN 分支里 `gcode_ready` 在检查**之前就 return** | 即使将来把 `is_wan` 改成 `true`，这条路径**仍然绕过**；外网可让机器下载任意 G-code 并进入"待确认" |
| **P0-3** | 后端 MQTT 默认 **`ws://` 明文** + 硬编码 `admin/admin123` | 凭据与指令明文过网；默认口令若未改，结合 P0-1 = 机器可被远程操控 |

**结论**：App 侧这轮（含我昨晚修的 P0）做事是对的，但**App 门禁只能挡"规矩的 App"**；
真正的闸门在固件与后端，而**两处目前都不设防**。建议把 P0-1/2/3 作为本周最高优先级，由固件+后端各出一人当天认领。

## 三、矛盾清单（逐条带证据）

### 🔴 P0（阻断/安全，建议 24h 内认领）

**P0-1　外网命令拦截"责任真空"**
- 固件：`main/cnc_net.c:2147` → `handle_command(data_buf, false);`（**MQTT 路径硬编码 `is_wan=false`**），
  注释原文："cloud gateway is the sole WAN entry; it applies the …"；且 `:73` `g_wan_allow_all = true`（默认全信任）。
  ⇒ `is_wan_forbidden()`（`:1347`）**永远不执行，是死代码**。
- 后端：全库 grep 无 `whitelist`/`forbidden` 相关命令过滤（命中的都是登录鉴权）；
  `DeviceMqttSyncService` 仅发布 register / acl / toolMap。
- 契约：`app_view.json` 的 `wan_whitelist` 定义了清单，**但没写"由谁执行"**。
- **影响**：持 broker 凭据者从外网可下发 `jog`/`home`/`setWorkZero`/`spindle`/`job start`/`prepare_job` → **机器动刀**。
- **建议**：① 固件改 `is_wan=true`（自身拦截，它是最后一道）；② 后端网关对下行命令做白名单二次校验（纵深）。两者都做，不要二选一。

**P0-2　`gcode_ready` 绕过所有检查**
- 证据：`cnc_net.c:1393-1398` —— 只要 `type == "gcode_ready"`，**先处理并 `return`**，位于 `is_wan_forbidden`（`:1416`）**之前**。
- **影响**：外网可让机器下载任意 G-code 并进入 `awaitingConfirm`；即便修好 P0-1 这条仍漏。
- **建议**：把 `gcode_ready` 与 `prepare_job` 一并纳入 WAN 判定。

**P0-3　后端 MQTT 明文 + 硬编码口令**
- 证据：`application-dev.properties:246-249`（`ws://43.154.192.242:8083/mqtt`、`admin`/`admin123`；`application-local` 同）。
  固件侧也有兜底硬编码口令 `demo123`（`cnc_net.c:2225`）。
- **影响**：口令/指令明文过网；默认口令若未改 → 结合 P0-1 可远程操控机器。
- **建议**：恢复 `ssl://…:8883` + 强制改密 + 凭据移出源码（环境变量**不给默认值**，缺失即拒绝启动）。

| P3-3 | `toolMap`/`leveling` 两端安全判断相反 | App 视为"契约未列 ⇒ 同网限定"，固件注释视为"运营可远程下发" → **需昊总拍板** |

## 四、根因分析：为什么会对不上

1. **没有单一契约源**。现在至少三份"圣经"：App 的 `contract/views/app_view.json`、固件的《小屏幕支持命令完整清单》、驱动/Web 侧的《MQTT 消息格式手册 §3.1》。三者对 `state` 词表、`progress` 口径、命令命名的说法都不同。
2. **文档滞后于实现，且滞后方向不一致**。已实证固件文档滞后于固件代码（`prepare_job` 已支持但文档未写），也滞后于 App 代码（App 09-04 已修完 `reset`/`softReset`/`reqId`/`axes`，固件文档仍在"要求 App 修"）。
3. **安全责任边界未定义**。固件把 WAN 拦截"留给云网关"，后端没接这个活 → 真空。契约只写了清单，没写执行方。
4. **各端按自己的理解"多做/少做"**：App 把"契约未列 ⇒ 同网限定"作为兜底（更严），固件把"运行期配置"视为可远程（更松）——同一命令两种安全等级。
