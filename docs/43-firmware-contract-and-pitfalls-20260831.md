## 一、运动安全铁律（最高优先，不可协商）

### A1 🔴 运动安全必须下位机闭环，网络命令不参与

- **owner 已明确**：「App 断链肯定不能影响雕刻；雕刻由屏幕主控并监控，屏幕经 MQTT 广播过程，屏幕/App/PC 谁亮着谁接收」（`docs/39` §零之二 第 6 条）。
- **Feed Hold / 急停 / 限位 / 仓盖 / 防护门**，全部由屏幕·主控本地闭环。
- 若产品上确有"远端失联停机"需求，只能是：**显式可选策略 + 默认关闭 + 分钟级阈值**，绝不能是 15 秒级。

> ⚠️ **为什么这是铁律**：App 心跳周期 10s，若固件阈值 15s，只有 5 秒余量。
> 客户锁屏、切微信、家里 Wi-Fi 抖一下 → 雕刻中断 → **工件报废**。
> 而雕刻本身是本地文件闭环，根本不需要 App 在场。

### A2 🔴 `state` 字段是 App 的安全闸门，绝对不能失真

App 侧（`lib/models/machine_status.dart:127`）：

```dart
bool get canControl => state == MachineState.idle;
```

**Jog / 运动控制的唯一放行条件就是 `state == idle`。**

历史上真实发生过的安全漏洞：摄像头发了只带 `{"streaming":true}` 的帧到状态主题，
`MachineStatus.fromJson` 对不认识的字段回落成默认值 → **加工中的 `state` 被刷成 idle → Jog 被错误解锁**。

**要求**：
- 状态帧**必须**由主控真实状态驱动，任何来源（自检、网络、摄像头、UI）都不得写入假的 `state`；
- 网络断连时发 `disconnected`，**不要**回落成 `idle`。

### A3 🔴 禁止任何"自动检测 + 自动补发"的逻辑

前车之鉴（真实事故）：中继 `relay.py` 曾有「看到没画面就帮忙补发一条 `stream_start`」的自愈逻辑，
在按需推流下变成**每 3 秒强推一次的死循环**，几乎拖垮链路。

**判据**：**能自动触发的，不给权限；由人触发的，可以给。**

| 角色 | 能否发流控/运动指令 |
|---|---|
| 自动自愈 / 中继型节点 | ❌ **绝对禁止** |
| 云网关 `svc-bridge-aliyun-api` | ✅ 允许，但**仅限响应用户显式操作** |
| App / 屏幕本地按钮 | ✅ 允许 |

### A4 暂停 / 继续必须回显真实状态

App 的暂停/继续是**乐观 UI**（点一下本地按钮立即翻转）。若命令被 ACL 静默丢弃或固件未执行，
会出现「App 显示已暂停、机器还在跑」的错位。

**要求**：任何状态变化都要**在下一次状态帧里回显真实值**，不要只在收到命令时回一次。

### A5 急停优先级最高，且必须本地可触发

机身物理急停 > 任何网络命令。急停后必须进入 `alarm` 状态并广播，不接受网络端的自动恢复。

### A6 雕刻中禁止 OTA / 重启

OTA 前必须检查 `state`；`busy` / `paused` 状态下拒绝升级（见 `docs/03` §10.13 OTA 契约）。

## 二、身份与主题契约

| # | 项 | 约定 | 说明 |
|---|---|---|---|
| B1 | 设备码 | 屏幕 = 摄像头 = 阿里云，同一个字符串 | 格式需满足 `^cam-[a-z0-9-]+$` 正则（**小写**）；含大写会直接不匹配 ACL |
| B2 | clientId | `screen-<deviceId>` | |
| B3 | username | `screen-<deviceId>` | 与 clientId 同构 |
| B4 | 订阅 | `cnc/<deviceId>/cmd`、`cnc/broadcast/#` | 订阅了就要处理，否则取消订阅（省资源、避免排查误导） |
| B5 | 发布 | `cnc/<deviceId>/{status,notify,telemetry,log}` | |
| B6 | LWT | topic `cnc/<id>/status`，载荷 **`{"state":"disconnected"}`**，QoS1 + retain | ⚠️ **不能发纯字符串** `"offline"` —— App 解析非对象会当 idle，掉线显示成在线 |

### B7 ⚠️ 同一个 `cnc/<id>/cmd` 主题上有三种帧，必须精确区分

终局方案下机器命令、摄像头命令、心跳**共用同一个主题**，靠 payload 区分：

| 来源 | 帧 | 屏幕该怎么处理 |
|---|---|---|
| App → 机器 | `{"cmd":"jog",...}` | ✅ 处理 |
| App → 摄像头 | `{"action":"stream_start"}` | ❌ **必须忽略** |
| App 心跳 | `{"cmd":"hello"}` | 仅更新"App 在线"，**不得触发任何运动/复位动作** |

**要求**：用**字段精确匹配**（先判 `cmd` 字段存在且是字符串），
**不要用子串搜索**（`strstr`）—— 摄像头端已因 `strstr` 误触发风险改成了 `json_get_action()`，屏幕同理。

## 三、状态帧字段级防坑 ★（最容易中招，逐条核对）

> 依据：`PROTOCOL.md` §2.3（`:128-155`）与 App 解析 `lib/models/machine_status.dart:138-191`。

### C1 ⚠️ `spindle` 字段 —— 协议文档自相矛盾，固件必须绕开

**冲突事实**：

| 出处 | 说法 |
|---|---|
| `PROTOCOL.md:152` | `spindle` 是 **bool**（主轴是否运转）；转速继续用 `rpm` |
| `PROTOCOL.md:449` 示例帧 | `"spindle": null` |
| `PROTOCOL.md:461` 示例帧 | **`"spindle": 12000`** ← 仍在当数值用 |
| App `machine_status.dart:164` | `final rpmRaw = j['rpm'] ?? j['spindle'];` ← 当转速别名 |
| App `machine_status.dart:188` | `spindleOn: j['spindle'] == true,` ← 当 bool |

**后果（两种写法都会丢一半数据）**：

| 固件发什么 | App 实际效果 |
|---|---|
| `"spindle": 12000` | 转速 ✅ =12000，但 **主轴运转标志 = false** ❌ |
| `"spindle": true` | 运转标志 ✅，**转速 = null** ❌ |
| `"rpm": 12000` 单发 | 转速 ✅，**运转标志 = false** ❌ |

✅ **正确做法：两个字段都发，各司其职**

```json
{ "rpm": 12000, "spindle": true }
```

### C2 🔴 `state` 只能发枚举内的 6 个值，越界会静默回落成 `idle`（安全相关）

App 枚举（`machine_status.dart:5-12`）：

```
disconnected | idle | homing | busy | paused | alarm
```

而 `PROTOCOL.md:430` 的状态机里还有 **`download`** 和 **`ready`** 两个阶段 ——
**这两个不在枚举里**。App 的解析（`:140-146`）找不到匹配时**保持默认 `idle`**。

**后果**：下载中 / 就绪时 `state` 被当成 `idle` → `canControl = true` → **Jog 被错误解锁**。

✅ **正确做法**：
- **禁止**发 `download` / `ready` 等枚举外的值；
- 下载进度用 `download` 字段（0..1）表达，`state` 保持 `busy` 或 `idle`；
- "就绪待确认"用 `awaitingConfirm: true` 表达。

### C3 ⚠️ `scIndex` / `scTotal` 不能常驻，否则自检永远结束不了

App 判定（`machine_status.dart:130-131`）：

```dart
bool get selfCheckDone => scTotal > 0 && scIndex >= scTotal;
```

若固件一直发 `{"scIndex": 0, "scTotal": 5}`，App 会永远显示「自检中 0/5」。

✅ **正确做法**：**只在自检期间**发 `scTotal: 5`；非自检阶段发 `scTotal: 0`（`scIndex: -1`）。
`PROTOCOL.md:139` 已写明「`scTotal` 为 0 = 无/未上报」。

### C4 ⚠️ `progress` 必须是 `0..1`，不能发 `0..100`

App 侧（`machine_status.dart:174`）：`prog.clamp(0.0, 1.0)`。

发 `42` 会被 clamp 成 `1.0` → **进度条瞬间满格**。

### C5 ⚠️ 两个字段是下划线命名，不是驼峰

| 正确 | 常见错误 |
|---|---|
| `alarm_code` | ~~`alarmCode`~~ |
| `grbl_online` | ~~`grblOnline`~~ |

写错 App 会静默取默认值 0 / false，**不报错、极难排查**。

### C6 `download` 字段目前无人消费

`PROTOCOL.md:140` 定义了 `download`（0..1 下载进度），但 App 的 `MachineStatus`
**没有这个字段**（`machine_status.dart:16-78` 全部字段清单里没有）。

→ 下载进度**在 App 上看不到**。
**需要拍板**：App 补字段（推荐，客户需要看到"正在准备文件"），还是固件改用 `msg` 文本提示。

### C7 建议发但非必须的两个字段（能显著提升可观测性）

| 字段 | 用途 |
|---|---|
| `job` | 当前加工任务文件名（如 `logo.nc`），空闲/未知为 null |
| `error` | 报警原因；字符串，或 `{"msg":"...","code":"..."}` |

### C8 `awaitingConfirm` 是防呆横幅的唯一来源

机旁物理确认时置 `true`，App 会弹横幅。量产形态下由**机身屏物理按钮**触发（`PROTOCOL.md:118`），
`{"cmd":"confirm"}` 仅供联调模拟，量产固件可忽略。

## 四、命令帧契约

| # | 命令 | 说明 |
|---|---|---|
| D1 | `{"cmd":"job","action":"start"}` | 触发执行**已落盘**的 G-code。⚠️ **App 不发 G-code** |
| D2 | `{"cmd":"job","action":"prepare","gcodeUrl":"...","compensation":"firmware"}` | 先下载落盘，再走确认→自检→加工 |
| D3 | `{"cmd":"leveling","mode":1,"cols":5,"rows":4}` | `cols/rows` 由 App 按云端下发的**真实模型尺寸**算好 |
| D4 | `{"cmd":"toolMap","tools":[...]}` | 刀仓映射；固件只校验物理在位 |
| D5 | `{"cmd":"hello"}` | 心跳。**只更新在线状态，不触发任何动作** |
| D6 | `{"action":"stream_start"/"stream_stop"}` | **不是发给你的**，请忽略 |

### D7 🔴 资产闭环不变式：App 永不持有 G-code

`PROTOCOL.md:161-163`：MQTT/TCP **只传控制指令与下载链接，不传文件本体**；
G-code 一律经 HTTP 下载落盘后执行，**不做流式/滴流传输**。

### D8 双 G-code 路径 —— 每次任务**只能有一个补偿方**

| 路径 | 来源 | 补偿方 |
|---|---|---|
| 一 | 本地设计 → 上位机 | `compensation: host` |
| 二 | 云端模型库 | `compensation: firmware` |

⚠️ **重复补偿会直接废工件**。固件必须：读到 `compensation` 字段后据其决定是否补偿，
**不得在已补偿的基础上再补一次**。

## 五、配网与量产（方案 C）

### E1 配网职责在屏幕（owner 已定）

App **不做配网、不加蓝牙**。屏幕完成搜网入网。

### E2 配网时同时向摄像头下发四项

```
屏幕配网成功
   ↓ 同一条 UART 通道
SSID + 密码 + 设备码 + 摄像头推流 token
   ↓
摄像头存 NVS，各自连 Wi-Fi
```

> 客户**只配一次**。详见 `docs/39` §七（方案 C）与 `docs/40` §12（推流 token）。
> ⚠️ 推流 token 与设备码**是同一次固件改造**，别让摄像头烧两次固件。

### E3 UART 引脚以摄像头端为准

摄像头端 provisioning UART 已迁到 **GPIO 22/23**（旧版 13/14 与摄像头 PCLK/D0-D2 冲突）。
屏幕侧新开 UART 时**与摄像头端对齐**，不要各定各的。

### E4 设备码写入 NVS，必须可覆盖、幂等

- 支持重复下发（客户重新配网时应覆盖旧值）；
- 写入后需重启连接才生效时，要**先停旧连接再建新连接**（见 F2）。

### E5 产线串口写入作为保底手段

方案 C 之外，保留产线/售后用串口指令写设备码的能力（返修、换板场景必需）。

### E6 未配网 / 未绑定时**不要连 MQTT，更不要疯狂重试**

⚠️ 前车之鉴（真实事故）：摄像头端在 token 丢失时**每 200–400ms 重连一次**，几乎拖垮整条链路。

未绑定时应**静默等待**，或采用**指数退避**（起步 ≥5s，上限 ≥5 分钟）。

### E7 凭据生产化

量产不能沿用 `demo123` 这类共享密码。方向由 MQTT 侧定（HTTP 认证 / 设备自注册，见 `docs/41` M-7），
固件需配合支持**凭据可配置、可下发**。

## 六、重连与异常处理

| # | 场景 | 要求 |
|---|---|---|
| F1 | 网络断开重连后 | 必须**主动重发一次完整状态帧**（retained 的可能是断线前的旧值） |
| F2 | 设备码变更 | **先 stop 旧连接再重连**；否则旧 clientId 仍在线会被 broker **同名互踢** |
| F3 | GRBL 掉线 | 广播 `grbl_online: false`，`state` 转 `alarm` 或 `disconnected`，**不要假装 idle** |
| F4 | UDP beacon 的 IP | **每轮广播前重新读取**，不要只在任务启动时取一次（重连换 IP 后会广播旧地址） |
| F5 | 收到无法解析的帧 | 记录并忽略，**不要复位、不要重启、不要停推** |

## 八、给固件端的一句话总结

> **配网与量产**
> 9. 配网在屏幕做，App 不做配网不加蓝牙。配网时经 UART 把 **SSID+密码+设备码+推流 token** 一起下发给摄像头（UART 引脚对齐摄像头的 GPIO 22/23）。

> 11. 设备码变更时**先停旧连接再重连**，否则旧 clientId 在线会被同名互踢。
>

> 12. 同一 `cnc/<id>/cmd` 主题上混跑三种帧（机器 `cmd` / 摄像头 `action` / 心跳 `hello`），请**按字段精确匹配**，不要用子串搜索；心跳只更新在线状态，不得触发任何动作。
> 13. App 永不持有 G-code，只发下载链接；双路径下**每次任务只能有一个补偿方**，重复补偿会废工件。
> 14. 重连后要主动重发一次完整状态帧；UDP beacon 的 IP 要每轮重取。
