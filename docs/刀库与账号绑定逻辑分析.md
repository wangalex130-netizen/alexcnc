# 刀库真值 / 自定义刀具 / 个人账号绑定 · 逻辑分析

> 同步对象：APP（Flutter）/ 固件（ESP32-S3 + GRBL）/ MQTT 服务器 / 阿里云 API 四方  
> 来源：2026-08-14 与工程师讨论的刀库同步、自定义刀、账号绑定三议题  
> 衔接：本分析与《三任务一致性终稿》§4/§9/§16/§17 同义，补充"刀库"一词的二次拆解。

---

## 0. 一句话结论

工程师的三段逻辑**主体都成立**，但需把"刀库"这个词拆成**两层不同的真值**，否则联调会踩三个坑：

1. **刀库目录（Catalog）**——有哪些刀、每把参数。这是**资产数据，阿里云为唯一真值**，MQTT 只做广播同步。机器本地只存**派生缓存**，不是权威。
2. **刀仓实载（Slot State）**——4 个卡槽此刻各插了哪把。这是**机器运行时真值**，由 4 个传感器（presence）+ 操作员 `tool_map` 映射共同决定，机器拥有。
3. **自定义刀**——驱动只生成 5 把 3.175 刀路，**设计流程内严禁自定义**；仅外部 G-code 模式允许"未认证/手动"占位。
4. **账号绑定**——machineCode 是物理唯一 ID，账号是 owner，所有个人设置（含刀库）作用域 = 该 machineCode。

---

## 一、刀库"真值"问题（核心）

### 1.1 必须先拆清的两个概念

| 概念 | 含义 | 真值归属 | 修改方 | 同步方式 |
|---|---|---|---|---|
| **刀库目录 Catalog** | 系统里有哪些刀 + 参数（直径/类型/张角/材质建议…） | **阿里云 DB（唯一权威）** | APP / 网页 / 屏幕任意端编辑 | 阿里云 publish → MQTT 广播 |
| **刀仓映射 ToolMap** | 这台机器 4 个卡槽此刻各插哪把 | **机器（运行时）** | 操作员在 APP/屏幕设定，下发 `tool_map` 命令 | 命令直达 `cnc/<deviceId>/cmd` |

> ⚠️ **工程师的疑问"机器刀库真值是不是不存在了"——答案是：目录真值确实不存在于机器本地（云为权威）；但机器拥有另一层真值：物理刀仓状态（occupancy + 映射）。两者互补，不冲突。**

### 1.2 广播链路（正确 ✅）

```
任意端编辑刀库目录 → 阿里云 DB 落库
        → 阿里云作为 broker 客户端 publish cnc/<deviceId>/tool_catalog（retain=true）
        → MQTT 广播 → APP / 网页 / 屏幕 / 机器 各自刷新本地缓存
```

- 主题建议：`cnc/<deviceId>/tool_catalog`（目录是 per-machine，见 §三），`deviceId == machineCode`。
- `retain=true`：新订阅的端（如刚联网的机器）上线即拿到最新目录，不必等下一次编辑。
- 阿里云必须是腾讯云 broker 的客户端（admin/bridge 身份）——这点与《终稿》§16/§17 一致，否则"编辑落库了但 broker 不知道要广播谁"。

### 1.3 机器读表时机（正确，但有缓存约束 ⚠️）

工程师说"开机 / 雕刻开始 / 雕刻结束 / 关机读取刀库表"——这是**读目录缓存**，不是实时拉云。两个隐含要求：

1. **机器必须有本地目录缓存**：首次从云拉全量，之后每次 `tool_catalog` 广播覆盖。纯 LAN / 云不可达时，机器用本地缓存照常工作。
2. **缓存是"派生"，不是"权威"**：云端永远是唯一真值；机器绝不允许反向把本地改动当成目录权威写回云（那是 ToolMap 的职责）。

### 1.4 传感器匹配的边界（**最容易炸的坑** ❗）

4 个传感器只能探测**"有没有刀"（presence）**，**识别不了"是哪把刀"（identity）**。这导致：

| 场景 | 传感器能发现吗 | 结果 |
|---|---|---|
| 目录说槽1应有刀X，传感器说槽1**有刀** | ✅ 通过 | 匹配成功 |
| 目录说槽1应有刀X，传感器说槽1**空** | ✅ 异常 | 硬阻止：`missing_tool` 通知屏幕 |
| 操作员**插错了刀**（槽1实际是刀Y） | ❌ 发现不了 | 传感器说"有刀"→误判通过 |

**结论**：传感器只提供"在/不在"级安全，**不提供"对不对"级安全**。目录里的"槽→刀"映射是**操作员 / `tool_map` 命令设定的，不是自动识别的**。

**建议防御设计**：
- 异常分级：① **缺失**（传感器空但应有）→ 硬阻止，禁止开切；② **错刀**（无法自动发现）→ 靠操作员确认 + 加工前 `confirm_required` 强确认。
- 在 W4（定原点/防撞）步骤内嵌一次**强制刀仓校验 + 确认**，把"插错刀"的人为风险压到最低。

## 二、自定义刀具 & 3.175 限定

### 2.1 事实约束（不可动摇）

- 夹具**只支持 3.175mm**；
- 驱动**只生成 5 把 3.175 刀的刀路**（平底 / 球头 / 30° / 60° / 90° V）。

### 2.2 逻辑推导

**官方目录 = 严格 5 把 3.175**（服务端强制，设计流程内不可增删、不可自定义）。

**自定义刀分两种情形，必须区别对待：**

| 情形 | 是否允许 | 理由 |
|---|---|---|
| (a) 我们的"设计→雕刻"流程内自定义刀 | ❌ **禁止** | 驱动不会为它生成刀路，加了也是死数据。应禁用/隐藏"添加自定义刀"入口 |
| (b) 外部 G-code 导入模式 | ✅ **允许（受限）** | 客户用别的 CAM（如 6mm 刀、非标 V）生成 G-code，自己手动换上未认证刀。系统只需一个"手动/未知刀"占位 + 操作员断言槽位，**不进驱动、不进材质推荐** |

### 2.3 建议落地口径

1. 官方刀库目录**锁死 5 把 3.175**，服务端 + APP + 屏幕三端同源，不可增删。
2. 若未来要开放"自定义刀"，只能是明确标注的 **「未认证 / 手动」** 项，且一旦选中它：
   - **禁用驱动刀路生成**；
   - **强制切换到外部 G-code 模式**；
   - **退出材质推荐**（19 种材质参数表也是按 3.175 + 5 刀设计的，自定义刀无匹配）。
3. 保持驱动范围干净：我们的目录永远只描述"驱动能用的刀"，客户自己的刀走"外部 G-code + 手动槽位"旁路。

> 一句话：**列表里只放官方 5 把；客户想用别的刀，自己从外部软件出 G-code、手动换刀，我们的列表不认、也不该认。**

## 三、个人账号 & 机器绑定

### 3.1 流程梳理（确认无误 ✅）

```
① 网页注册个人账号（accountId）
② 机器首次联网 → 服务器记录 machineCode（硬件唯一 ID）→ 机器进入"已注册"态
③ 客户在 APP 输入/扫码机器码 → accountId ↔ machineCode 关联 → 绑定成功
④ 绑定后，该机器所有个人设置（刀库、偏好…）都在 machineCode 唯一 ID 下
```

### 3.2 归属模型（清晰）

- **机器 = 物理唯一 ID（machineCode）**；
- **注册 = 机器联网，服务器获知 ID**（连接层声明，非业务绑定）；
- **绑定 = accountId ↔ machineCode（DB 关联）**，账号是 owner；
- **设置作用域 = per-machine（machineCode）**：一台机器一个物理刀仓，刀库天然 per-machine；一个账号可拥有**多台**机器。

### 3.3 与 MQTT 契约的衔接（呼应《终稿》§16/§17）

- 设备主题 `cnc/<deviceId>/...`，**`deviceId == machineCode`**；
- 绑定成功 → **阿里云（持有账号/绑定/刀库 DB）必须作为腾讯云 broker 客户端**，把 `accountId → machineCode` 映射写成 broker **ACL**，授权：
  - 该账号的 MQTT 客户端（APP/网页）访问 `cnc/<machineCode>/#`；
  - 该机器的 MQTT 客户端（`screen-<machineCode>`）访问自己的 `cnc/<machineCode>/#`；
- 刀库变更广播同理：阿里云以 admin 身份 publish `cnc/<machineCode>/tool_catalog`。

### 3.4 账号侧的"刀库"语义

- 刀库目录按 **machineCode** 存储（每台机器各自一份）；
- 账号通过"拥有 machineCode"间接拥有其刀库；
- 多机器账号：每台机器独立刀库，互不影响。

## 四、三方契约需要补的条目

在《三任务一致性终稿》基础上，补：

1. **新增主题**：`cnc/<deviceId>/tool_catalog`（retain=true，广播目录）。
2. **明确两层真值**：Catalog（云权威）/ ToolMap（机器运行时），禁止机器反向写 Catalog。
3. **缓存策略**：机器本地目录缓存为"最后已知好"，云不可达时用缓存，但标脏（dirty）提示。
4. **异常分级**：`missing_tool`（硬阻止）/ `wrong_tool_risk`（靠 confirm）。
5. **自定义刀开关**：默认关；开则强制外部 G-code 模式。
6. **ACL 同步**：阿里云绑定/解绑事件 → broker ACL 自动增删。

## 六、四项跨云决策（2026-08-14 由 App 任务拍板，与《终稿》§18 同义）

对应《终稿》§17 原 Q1–Q4：

| # | 决策点 | 拍板结论 |
|---|---|---|
| Q1 | 阿里云 ↔ Broker 连接方式 | **常驻 bridge 持久客户端 `bridge-aliyun`**（单一通道），不引入 broker REST admin 面 |
| Q2 | 刀库更新是否推 toolMap | **否**——目录更新只广播 `tool_catalog`（retain），绝不推 `toolMap` |
| Q3 | G-code 文件服务位置 | **统一阿里云**（存储/服务/push 编排同云；机器 HTTPS 下载，broker 只传 URL） |
| Q4 | ACL 同步失败重试 | **至少一次 + 幂等 + 持久补偿 + 重连重放 + 5min 周期对账**（详见《终稿》§18 Q4） |

### 对四方的影响
- **阿里云 API**：实现 `bridge-aliyun` 长连接客户端；`acl_sync` 持久队列 + 重试；刀库更新只发 `tool_catalog`、不发 `toolMap`；G-code 文件服务归位阿里云。
- **MQTT 服务器**：broker 认证后端消费 `cnc/sys/acl` 控制消息并应用 ACL；提供 `cnc/sys/acl/ack` 回执；保留 `tool_catalog` 广播通道。
- **固件**：订阅 `cnc/<deviceId>/tool_catalog` 刷新本地目录缓存（派生、不回写）；G-code 改从阿里云 HTTPS 拉取。
- **App**：订阅 `cnc/<deviceId>/tool_catalog` 刷新本地刀库；刀库列表锁死官方 5 把（见前文，已落地 `tool_library.dart`）。
