
## 一、P0 · 阻塞量产 / 安全事故（必须解决才能卖）

### P0-1 🔴 摄像头画面可被任意人观看（隐私事故）

**事实链**（全部读代码/配置得出）：

| 环节 | 现状 | 出处 |
|---|---|---|
| 中继拉流 token | **硬编码在 App 里**：`lunyee-cnc-relay-7k2p` | `app/config.dart:34-37` |
| token 是否按设备/账号区分 | **否**，所有设备共用同一个 | 同上，全局单一常量 |
| 中继是否校验"该账号有权看这台设备" | **否**，`REQUIRE_BINDING` 未开启 | `machines_service.dart:53-54` 注释：「缺省为空 = 兼容期 demo 放行」 |

**后果**：任何人只要知道这个 token（**逆向 APK 就能拿到明文**，或从摄像头端问一句就有），
即可访问：

```
http://39.106.144.53:8080/stream/<任意设备码>?token=lunyee-cnc-relay-7k2p
```

查看**任意一台**客户机器上的摄像头画面。客户装在工作室/家里的摄像头被陌生人实时观看。

**这不需要黑客技术**，只需要把 APK 解包。

**处置（两端必须一起做）**：
- 阿里云：**P-2 必须提前到 P0** —— 登录后下发**按账号签发**的 token（JWT，含 userId + 允许的设备列表 + 有效期）
- 中继：开启 `REQUIRE_BINDING`，校验 `user=` 参数与 token 中的设备权限
- App：不再使用硬编码 token，改用登录后下发的（**我这边改，但要等后端先给接口**）

> 现状是"demo 兼容期"设计，**在卖第一台机器之前必须换掉**。

### P0-2 🔴 客户无法自助注册账号

**事实**：`login_page.dart:6/102` 明确注释「2026-08-21 工程师确认：App 不开放注册功能，登录页隐藏注册入口」。
`auth_service.dart:16` 也写「`POST /api/auth/register` 为方案 A 假设，**后端当前未开放注册**」。

**后果**：B2C 客户买了机器、装了 App，**没法自己创建账号**。
只能靠人工在后台开户再把账号密码发给客户 —— 这在批量销售下完全不可行。

**这是量产的硬阻塞**，优先级高于目前所有的 MQTT/摄像头细节。

### P0-3 🔴 机器档案必须人工在后台创建

**事实**：`machines_service.dart:120-121` 注释「线上后端要求先有机器档案（machineId），扫码只能匹配账号中**已创建**的机器」。
且实测账号列表里有一台「**未配置机器码**」——说明人工建档流程会漏字段，且**没有校验拦截**。

**后果**：客户拿到机器扫码绑定 → 后端没有这台机器的档案 → 绑定失败。
流程断裂，且客户不知道发生了什么。

**需要阿里云回答**（这决定了整个开机流程怎么设计）：
1. 机器档案是**工厂出货时批量导入**，还是客户扫码时**自动创建**？
2. 机器码（如 `cnc-demo-03`）由谁生成、写在哪台设备上？
3. 扫码时若档案不存在，能否自动建档并与当前账号绑定？

### P0-4 🔴 摄像头设备码硬编码在固件里，无法批量生产

**事实**：摄像头端回报「设备码固件里**三处强制赋值**」（`grep` 二进制确认 03×1 / 01×0）。

**后果**：每生产一台机器，都要**单独编译一次摄像头固件**并烧录。
这在产线上不可接受，也做不到"屏幕码 = 摄像头码"的一致性保证。

**量产方案**（需与摄像头端对齐）：
- 设备码改为**产线烧录进 NVS**（一次写入，固件通用）；或
- 设备自注册（provisioning）：首次上电用屏幕的唯一码去后端换 token，摄像头从屏幕获取

> 这正好是「5 道门」里的第 5 道 —— demo 期手工做可以，量产必须自动。

### P0-5 🔴🔴 契约冲突：雕刻不该被 App 心跳"绑架"（最高优先）

**用户要求（2026-08-31）**：

> 「APP 断链肯定不能影响雕刻，雕刻正常进行。雕刻过程由**屏幕**监控，屏幕经 MQTT
> 广播过程信息，屏幕/APP/电脑端谁亮着谁就接收实时信息。」

**但现有三端契约写的是**（这是白纸黑字，不是推测）：

| 出处 | 原文 |
|---|---|
| `docs/PROTOCOL.md:88` | 心跳 `{"cmd":"hello"}`（10s 一次）「**用于重置机器主控 15s Feed Hold 定时器**」 |
| `docs/PROTOCOL.md:215` | 「目的：重置机器主控 15s Feed Hold 定时器，避免用户长时间只监看不操作时加工被误暂停」 |
| `docs/36` §八第 8 条 | 「心跳 / Feed Hold：App 每 10s `{"cmd":"hello"}`，固件 15s Feed Hold」✅ 已列为"已对齐" |
| `hardware_service_real.dart:50` | 「固件 15s 内收不到任何命令即 Feed Hold；心跳周期取 10s 留安全余量」 |

**还有一条实测佐证**（`docs/34`：Jog 的 Z 按钮 bug）：

> 「点击会下发 `jog('z', 0)`（移动 0mm 的空命令），**还会刷新固件 Feed Hold 计时器**」

→ 说明固件实现是「**收到任何 `cnc/<id>/cmd` 命令就重置计时器**」，并非只认 `hello`。

**冲突的本质**：

```
旧架构（历史）          新架构（用户定义）
─────────────          ─────────────
App = 唯一控制端        App = 观察者之一
App 失联 → 无人看管     屏幕 = 主控，就在机器旁
→ 设计"失联即停"合理    → 失联即停 = 误伤
```

**为什么旧设计在今天是错的**（不止是体验问题）：

1. **违反既定的安全铁律**。项目 MEMORY 里明确写着：「**运动安全必须下位机闭环**」。
   而"靠 MQTT 网络心跳决定主轴/进给是否继续"恰恰是**把运动安全交给了网络** —— 违反铁律。
2. **网络不该参与安全判定**。Wi-Fi 抖动、手机锁屏、省电策略、地铁进隧道，都会让心跳断。
   这些都不是"机器该停下来"的理由。
3. **成本极高**：一个 40 分钟的工件，因为客户回了个微信而报废。

**建议的正确架构**（需固件端确认，App 不能单方面定）：

| 层 | 应该由谁负责 |
|---|---|
| **运动安全（Feed Hold / 急停 / 门禁 / 报警）** | **屏幕 / 主控本地闭环**，以物理信号与内部看门狗为准，与网络无关 |
| 雕刻过程执行与监控 | **屏幕**，并通过 MQTT 广播给各端 |
| App 心跳 `{"cmd":"hello"}` | **降级为"App 在线状态"**，供其他端显示"谁在看"，**不参与运动安全** |
| 若确实需要"远端失联则停" | 做成**显式可选安全策略**（默认关闭 + 阈值放宽到分钟级），而非常态 |

**需要固件端回答的一句话**：

> 「固件 15s Feed Hold 计时器，现在的重置条件是"收到任意 `cnc/<id>/cmd` 命令"，
> 还是有专门判定？如果是前者，请改为由屏幕/主控本地喂狗，网络命令不再参与。」

## 二、P1 · 可靠性 / 加工安全（会导致工件报废）

### P1-1 🔴 加工中网络抖动或锁屏 → 心跳中断 → 工件报废

**事实链**：

| 环节 | 数值 / 行为 | 出处 |
|---|---|---|
| 固件 Feed Hold 阈值 | **15 秒**收不到命令即进入 Feed Hold | `hardware_service_real.dart:50,671` 注释 |
| App 心跳周期 | **10 秒**发一次 `{"cmd":"hello"}` | `hardware_service_real.dart:51` |
| **安全余量** | **仅 5 秒** | 15 − 10 |
| MQTT 断线时的行为 | **`_publish` 静默丢弃，不报错、不通知** | `hardware_service_real.dart:636` |
| App 切后台/锁屏处理 | **完全没有**（全库仅 console_page 在 `resumed` 时探测网络，**无 `paused` 处理**） | `grep didChangeAppLifecycleState` 仅 1 处 |

**场景复现**：

> 客户启动一个 40 分钟的雕刻 → 中途锁屏去看别的东西 / 切到微信回消息 /
> Wi-Fi 抖了一下 → MQTT 断连或心跳发不出去 → **15 秒后固件 Feed Hold** →
> 主轴继续转但进给停止 → **工件烧糊 / 断刀 / 报废**。
> 而 App 端**没有任何提示**（`_publish` 直接 return）。

**这是客户视角下最严重的问题**：不是"用不了"，是"用着用着把料废了"。

**需要各端一起决定**（我不能单方面改）：

> ⚠️ **2026-08-31 更新**：owner 明确「App 断链不能影响雕刻」，与本条冲突已升级为 **P0-5**。
> 下面的"放宽阈值"只是治标；**正解是解除 App 心跳与运动安全的绑定**，见 P0-5。

| 方案 | 归属 | 说明 |
|---|---|---|
| A. 固件放宽阈值（15s → 60s+） | 固件 | 治标：降低误触发概率，但**锁屏超过 60s 仍会停** |
| **A+. 运动安全改为屏幕/主控本地闭环** | **固件** | **治本，见 P0-5。推荐** |
| B. App 加工中禁止锁屏 + 前台保活 | App | 治标，且违背客户使用习惯（加工几十分钟不让锁屏不现实） |
| C. 心跳断连时强提示 | App | 有价值，但只能"告知"，不能阻止停机 |

> **结论**：B、C 都不能解决根因。**必须以 P0-5 的方案（A+）为准。**

### P1-2 🟠 退后台未停止推流 → 摄像头持续推流

**事实**：全屏预览页只在 `dispose()` 时发 `stream_stop`。
客户按 Home 键退出时，**页面没有 dispose** → 我加的 30s 续租会一直跑 → 摄像头一直推。

**后果**：
- 违背"按需推流"的设计初衷（省带宽/省电/护隐私）
- 客户以为关了，其实摄像头还在拍

**修法**（App 侧，我可做）：监听 `AppLifecycleState.paused` → 发 `stream_stop`；`resumed` → 发 `stream_start`。
**但需注意**：加工中退后台不能停推（客户可能想边干别的边看监控）——需要区分"在看监控"和"不在看"。

> 建议口径：**退后台即停推**；客户回到前台自动恢复。加工中若需持续监控，走延时摄影而非实时流。

## 四、代码层校核结果（本次改动）

## 七、摄像头固件量产方案分析（owner 指定议题，2026-08-31）

### 7.1 先把约束摆清楚（这些是已定死的，方案必须服从）

| # | 约束 | 来源 |
|---|---|---|
| 1 | 设备码 = 屏幕 ESP32 唯一码 = 摄像头 ID = 共同 `deviceId` | 「统一机器码」决策（MEMORY） |
| 2 | 屏幕配网时**同时把 Wi-Fi 密码下发给屏幕 ESP32 和摄像头芯片**，两者各自连网，客户只配一次 | owner 2026-08-31 答复 |
| 3 | 摄像头必须随产品 ID **唯一绑定**，绝不允许别人看到画面 | owner 2026-08-31 答复 |
| 4 | 当前设备码在摄像头固件里**硬编码三处** | 摄像头端 2026-08-30 回报 |
| 5 | 屏幕与摄像头之间存在 UART 通道（摄像头端提到 GPIO19/20 串口配网） | 摄像头端 2026-08-30 回报 |

### 7.2 关键洞察（这条决定了方案选型）

> **约束 2 说：配网时屏幕已经通过 UART 把 Wi-Fi 密码发给了摄像头。**
> 那么——**同一条通道，完全可以顺带把设备码一起发下去。**

如果这个通道成立，就不需要在产线上给摄像头写任何东西。

### 7.3 三个方案对比

| 维度 | A. 摄像头厂家预刷（含码） | B. 我们工厂烧录（含码） | **C. 通用固件 + 配网时由屏幕下发（推荐）** |
|---|---|---|---|
| 摄像头厂家工作量 | 需按订单刷**不同**固件 | 刷通用固件 | 刷通用固件 |
| 是否需提前生成/传递码表 | **是**（码要提前给厂家） | **是** | **否** |
| 我方可控性 | 低（依赖厂家，易错） | 中 | **高** |
| 备货灵活性 | 差（摄像头与机器绑定） | 差 | **极好**（通用件任意调配） |
| 返修换摄像头 | 要找厂家重刷对应码 | 要返厂或现场烧录 | **换通用件，配网自动拿到正确码** |
| 产线设备投入 | 无 | **需烧录治具** | **无** |
| 「屏幕码 = 摄像头码」一致性 | 靠人工核对 | 靠人工核对 | **天然一致（由屏幕下发）** |
| 凭据保密 | 厂家掌握 | 自己掌握 | 自己掌握 |
| 换屏幕不换摄像头 | 失配，需重刷摄像头 | 失配，需重刷 | **重新配网即自动同步** |

### 7.4 推荐：方案 C

**流程**：

```
① 摄像头厂家：批量刷「通用固件」（不含设备码、不含凭据，只带"待配网"状态）
        ↓
② 我们工厂：只做装配，摄像头与屏幕装到同一台机器上即可，**零烧录**
        ↓
③ 客户首次开机，在屏幕上搜 Wi-Fi、输密码
        ↓
④ 屏幕经 UART 一次性下发「设备码(自身唯一码) + Wi-Fi 密码」给摄像头
        ↓
⑤ 摄像头存 NVS，用该设备码作为 MQTT username/clientId/推流设备号
        ↓
⑥ 屏幕与摄像头各自连 Wi-Fi → 摄像头在 MQTT 上以 cam-<设备码> 出现
```

**为什么 C 最好**：

1. **它是唯一能保证"屏幕码 = 摄像头码"天然一致的方案** —— 码由屏幕当场给出，不存在抄错、配错的可能。这正是约束 1 想要的效果。
2. **备货与返修最简单** —— 摄像头是通用件，仓库不用管它是配哪台机器；客户摄像头坏了，寄一个通用件过去，重新配网即可。
3. **产线零设备投入** —— 不需要买烧录治具、不需要维护码表。
4. **与已定的配网流程完全复用同一条通道**，几乎不增加工作量。

### 7.5 需要确认 / 加固的点（给摄像头端）

| # | 需确认 | 风险 |
|---|---|---|
| C-7 | 屏幕→摄像头的 UART 通道能否**同时下发设备码 + Wi-Fi 密码**（而不只是密码）？ | 这是方案 C 成立的前提 |
| C-8 | 设备码写入 NVS 后是否**每次配网都覆盖更新**？（换屏幕场景需要幂等覆盖） | 否则换屏后失配 |
| C-9 | UART 下发失败时的**降级手段**是什么？（起 AP 热点 / 产线串口工具） | 否则该机器变砖 |
| C-10 | 摄像头上电早于屏幕配网时，如何等待与重试？ | 时序问题 |
| C-11 | 设备码、Wi-Fi 密码在 NVS 中的**存储可靠性**（掉电保持、写坏恢复） | 已有先例：全擦 flash 丢 token |

> **建议同时保留一个保底通道**：产线用串口工具直接写入设备码。
> 万一客户现场 UART 下发异常，售后可以现场救回，不必返厂。

### 7.6 与「唯一绑定」的关系（约束 3）

方案 C 解决的是**设备码怎么来的问题**，但**不等于安全绑定**。
要真正做到"不能让别人看"，还需要（即 P0-1）：

- 后端下发**按账号签发**的拉流 token（含 userId + 允许的设备列表 + 有效期）
- 中继开启 `REQUIRE_BINDING`，校验 `user=` 与 token 中的设备权限

> 光有唯一设备码**不够**：设备码本身不是秘密（印在机器二维码上，客户扫码就是扫它）。
> **鉴权必须靠 token，不能靠设备码保密。**

## 八、方案 C 决策与摄像头端分工（2026-08-31 · App 轨核定）

### 8.1 🔴 先说紧急项：C-6 不是"建议做"，是"正在造成伤害"

摄像头端回报：`cam_mqtt.c:142` **每次 `stream_start` 都会 ABR reset + 重发 `streaming:true`，
没有 `s_streaming` 状态变量**（即**不幂等**）。

而 App 侧 A-6 续租**已于 2026-08-30 上线**（commit `129ac1af`，APK `alexcnc-129ac1af-A1A2A3A6.apk`）：
全屏预览页每 **30 秒**补发一次 `stream_start`。

**两者叠加的确切后果**：

```
App 每 30s 发 stream_start → 摄像头每次都 ABR reset
→ 画面每 30 秒重新协商/重载一次 → 客户看到周期性卡顿
```

**这不是潜在风险，是当前 APK + 当前摄像头固件的必然行为。**

> **处置**：C-6 验证通过前，**不要用 `129ac1af` 这个 APK 长时间看画面 / 给客户演示**。
> C-6 只需 10 分钟，应作为摄像头端第一优先，先于一切其他工作。

### 8.2 对摄像头端三个问题的答复

| 摄像头的问题 | App 轨答复 |
|---|---|
| 1. C-6 + C-11 + C-9 现在就改？ | ✅ **同意，且 C-6 提到第一位** |
| 2. 方案 C 确定走吗？ | ✅ **确定走 C**。理由见 8.3 |
| 3. 要不要双轨（先小改，等屏端）？ | ⚠️ **不要双轨**。理由见 8.4 |

### 8.3 为什么确定走方案 C（而不是 B / B'）

**核心理由：C-11 和方案 C 是同一个改造的两半，分开做等于改两遍。**

| 项 | 本质 |
|---|---|
| C-11「凭据加默认值」 | 硬编码 → **读 NVS，没有则用默认值** |
| 方案 C「设备码配网下发」 | 硬编码 → **读 NVS，没有则用默认值（占位）** |

两者是**同一套代码模式**。既然 C-11 一定要做，设备码顺手一起做，边际成本极低。

**收益**：摄像头固件里不再有任何硬编码设备码 → 直接变成通用件，
备货、返修、产线零烧录的收益**立刻兑现**，不必等任何人。

### 8.4 ⚠️ 纠正一个判断：C-7 **不必等屏端**

摄像头认为「C-7 摄像头端无能为力，必须先等屏端给 UART 命令格式」。**这个判断可以打破**：

| 摄像头端能单方面做的 | 是否依赖屏端 |
|---|---|
| ① 固件改为「读 NVS 设备码，读不到用占位默认值」 | ❌ 不依赖 |
| ② provisioning 解析器**现在就支持** `device` 字段（向后兼容，屏端发不发都不报错） | ❌ 不依赖 |
| ③ C-9 的 HTTP `/relay?device=...` 兜底写入 | ❌ 不依赖 |
| ④ 屏端升级为发送 `device` 后自动生效 | ✅ 依赖屏端（但只是"锦上添花"） |

**结论**：摄像头端**不必阻塞在屏端**。
做法是「**解析器先行，屏端后到**」——新字段向后兼容，屏端什么时候加，什么时候自动生效。
在屏端就位之前，靠占位默认值 + C-9 的 HTTP 兜底 + 产线串口工具照常可用。

> 屏端的改动其实很小：它原本就在发 `ssid`/`pass`，只需**多加一个 `device` 字段**。

### 8.5 需要摄像头端额外注意的两点

| # | 提醒 | 原因 |
|---|---|---|
| R-1 | **未绑定时不要连 MQTT，更不要疯狂重试** | 若 clientId 为占位值（如 `cam-unbound`），MQTT 认证必然失败。已有前车之鉴：token 丢失时摄像头 **每 200–400ms 重连一次**，几乎拖垮链路。未绑定状态应**静默等待**，不要重试风暴 |
| R-2 | **设备码变更时要先停旧连接再重连** | 摄像头自己已提到「clientId 变了要先 stop 旧的」（C-8），正确。补充：旧 clientId 若仍在线，broker 会因同名冲突把两个连接互相踢 |
