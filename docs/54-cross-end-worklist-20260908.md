| 2 | **删除接口** | 🔴 阻塞 | 已有 `flag`（0 删 / 1 有效）但没暴露接口。产品已拍板「客户可删」 |
| 3 | 材料 / 刀头名称 | 🟡 高 | 当前只有 `materialId`/`bitId`，App 列表只能显示数字 ID |
| 4 | `source` 细分 | 🟡 高 | 需区分「PC 自生成设计刀路」与「云端 G-code」，见 `docs/50 §3.6` |

| 6 | `gcodeUrl` / 重跑关联 | 🟢 中 | App 无本地生成 G-code 能力，**必须能重跑**（拓竹对标结论） |

### 1.2 推送

| # | 事项 | 说明 |
|---|---|---|
| 7 | 维护 binding 表 | `accountId ↔ deviceId`，**1:1**（一机一账号，见 `docs/53` 决策 2） |
| 8 | 四层寻址过滤 | 绑定关系 → 类型权限 → 偏好开关 → 得出目标 accountId |
| 9 | 个推 REST API v2 下发 | ⚠️ 五个坑见下节 |
| 10 | 离线消息有效期 | 建议 24h，过期不补（避免「三小时前的雕刻完成」） |
| 11 | 已读水位同步 | 单账号多设备**都收**，需云端统一已读状态 |
| 12 | 注销 / 解绑时清理 alias | 防止旧主人 / 离职员工继续收 |

> **个推 v2 下发五个坑（实测，务必照做）**
> 1. 签名 = `sha256(appkey + timestamp_ms + mastersecret)`，**不是 md5**
> 2. 鉴权头是独立 header **`token: <token>`**，不是 `Authorization`
> 3. 字段**下划线**：`request_id` / `push_message` / `click_type`
> 4. `request_id` **长度 ≥ 10**（用 uuid4）
> 5. 文案**不得含「个推」二字**（敏感词拦截）

## 3. PC 工程师

| # | 事项 | 优先级 |
|---|---|---|
| 1 | 上传 work record 时带 **`deviceId`** | 🔴 阻塞 |
| 2 | **自生成设计刀路必须上报云端**（`docs/50 §3.6`） | 🔴 阻塞 |
| 3 | 补删除接口 `POST /api/work/records/delete` | 🔴 阻塞 |
| 4 | 补材料 / 刀头名称（或字典接口） | 🟡 高 |
| 5 | 事件上报时**不判断**「该发给谁」 | ⚠️ 红线 |

> **第 2 条最容易漏**：PC 有两条发起路径——「调云端 G-code」（天然落库）与
> 「自生成设计刀路后直驱机器」。后者若绕过云端，统一流水会**静默丢数据**，
> 客户在 App 里就看不到这部分历史。

> **第 5 条**：寻址决策权 **100% 归云端**。PC / 固件只上报状态，不得自行判断接收方，
> 否则绑定关系一改就漏发或错发。

## 5. 依赖顺序（谁等谁）

```
云端补 deviceId + 删除接口  ──►  App 历史页完整可用
        │
        └──►  PC 上传带 deviceId + 自生成刀路上报
                    │
                    └──►  统一流水完整（App 能看到全部历史）

云端 binding 表 + 四层寻址  ──►  App CID 生命周期 + 已读同步
                                    │
                                    └──►  推送「该收的收到、不该收的不收到」
```

**关键路径**：云端补 `deviceId` 和**删除接口**是当前最卡的一环，建议优先排期。
App 历史页可先用 mock 数据并行开发，不阻塞。
