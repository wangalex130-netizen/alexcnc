# 49 · 决策记录：不实现「App 失联自动暂停」（2026-09-04）

**结论（owner 拍板）：不立项。机器自主跑完是产品根基，不做任何让雕刻执行依赖 App 在线性的改动。**

## 1. 背景与来源

- 早期协议设计（历史文档）曾规划：App 心跳 10s + 固件「15s 无命令 Feed Hold」看门狗。
- 2026-09-04 屏幕命令清单核对（闫安《小屏幕支持命令完整清单》+《App指令通讯待确认项通俗结论》）确认：**该功能固件从未实现**，`hello` 当前被直接忽略（§7.9），小屏无 15s FeedHold 逻辑。
- 因此这不是修 bug，而是「设计了但从未建设的功能」是否立项的决策。

## 2. 决策依据（客观事实）

### 2.1 现状（保持）
- 开始雕刻前 G-code 已整体下载到机器（`prepare_job` 文件清单帧 → `gcode_ready`），此后 App 掉线/关机/杀后台，**机器自主跑完，不受影响**。App 仅为监视器 + 遥控器（云端直推、App 只发 startJob 的既定架构）。

### 2.2 若实现该功能（反对理由）

| 维度 | 分析 |
|---|---|
| 核心价值场景 | 必须同时满足「无人值守 + 机器恰好出事 + 出的事能被暂停止损」三条件，很窄；且**暂停只停运动不停主轴**，起火类风险兜不住 |
| 核心冲突 | 客户自然用法是「点开始、关手机走人、回来看成品」；上线 = 关 App 即停机，动摇「机器自主」产品根基（owner 明确：这是最基础的功能） |
| 安全兜底 | 限位/急停/仓盖/防护门已是**下位机硬件本地闭环**（运动安全铁律①），不依赖 App；假安全感反而鼓励彻底无人值守 |
| 技术归属 | App 侧实现是伪命题（App 掉线则发不出暂停）；云端网关代发违反「自动触发→禁、人为触发→允」既定原则且让机器安全依赖云；**只有固件能做** → 量产前需固件+契约三端同步 |
| 误判代价 | 手机杀后台/MQTT 瞬断误判 → 激光暂停=原地灼斑、铣削暂停=驻留刀痕，一次误判废一件；恢复流程增加客诉 |

### 2.3 与既定原则的关系
- 与「FeedHold/急停/限位等全下位机本地闭环」铁律一致：本决策**不新增**任何 App/云驱动的暂停路径。
- 与 D8「禁自动检测+自动补发」及 EMQX「自动触发→禁」准则同一取向：机器执行不被远程链路状态自动干预。

## 3. 后续处理

- ❌ 当前迭代：不做，App/固件/云端均不排期。
- 📌 量产前评估（可选，默认关闭）：若届时出现真实「无人值守事故」数据，可评估做成固件侧**可选开关**（通俗名如「守护模式」，仅 busy 态生效、暂停后走 `awaitingConfirm` 门禁人工恢复、默认关闭）。在此之前不进入任何待办清单。
