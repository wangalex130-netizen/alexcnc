## 一、App 整体架构（三层 + 一个门禁）

```
┌─────────────────────────────────────────────────────────┐
│  App（Flutter）  UI / 状态 / 主题 / 图标（已全部完成）     │
│   图库 · 控制台 · 我的   （底部 3 Tab）                     │
│   向导 6 步 · 自检流水线 · 实时加工监控  （全屏流程，非 Tab）│
└───────────────┬───────────────────────┬──────────────────┘
                │ 调用抽象接口            │ 调用抽象接口
                ▼                        ▼
        HardwareService            CloudService
        （App ↔ ESP32 固件）        （App ↔ 云端 Smart CNC Studio）
                │                        │
        providers.dart 里把 Mock 换成 Real 即接真机
                │
        门禁：NetworkProbe 判定 isLocalLAN（同 Wi-Fi=全功能 / 公网=监视）
```

**铁律（已在代码里落地）**：

1. ESP32 是状态唯一真值源（SSOT），App 只渲染它广播的 `MachineStatus`。
2. 手机**绝不持有真实 G-code**：切片文件由云端经 LAN/MQTT 直推 MCU，App 只取轻量 `TaskMetadata` + 极简 2D 矢量（用于轨迹预览）。
3. LAN/WAN 门禁：同 Wi-Fi → 全功能（Jog/回零/开切）；4G/5G 公网 → 监视模式（Jog/开切锁死，仅监控+软停/暂停）。

## 二、功能逻辑全景（页面 → 碰哪些接口）

### 底部 3 Tab

| Tab | 页面            | 功能                                                 | 碰硬件/云端                                   |
| --- | ------------- | -------------------------------------------------- | ---------------------------------------- |
| 图库  | `LibraryPage` | 灵感库（公开）+ 我的空间 + 历史记录；点模型进入向导                       | `CloudService.getInspiration/getMySpace` |
| 控制台 | `ConsolePage` | 实时监控区 + 快捷开关（照明/红点激光/延时）+ DRO + Jog/主轴/ATC + 停止/暂停 | `HardwareService` 几乎全量                   |
| 我的  | `ProfilePage` | 账号/设置/诊断上报                                         | `CloudService.pushDiagnostics`           |

### 全屏流程（从图库点模型进入，非 Tab）

1. **向导 6 步**（`WizardPage`）：解析任务 → 材质确认 → 刀仓映射 → 定原点防撞 → 智能调平 → 开始雕刻。
   - 入口：`CloudService.getTaskById(id)` 取 `TaskMetadata`（尺寸/材质/刀具/工序）。
   - Step3 刀仓映射、Step4 定原点都调 `HardwareService`（ATC 同步、读 `getWorkArea`、Jog 红点、走边框）。
   - Step6「开始自检并雕刻」→ 启动全局 `activeJobProvider`，先跑自检流水线，再 `startJob()`。
2. **自检流水线**（`SelfCheckPage` + `providers.dart` 全局驱动）：可视化展示阶段进度；完成后自动跳监控页。
3. **实时加工监控**（`JobMonitorPage`）：进度/遥测/2D 轨迹/暂停/停止；顶部叉号只关页不停止加工（状态由全局 `activeJobProvider` 维护，可在控制台「当前加工中」重新进入）。

> ⚠️ **待确认①**：你原始需求写的是「手机雕刻流程固定 **5 步**」，但代码实现是 **6 步**（解析任务 / 材质确认 / 刀仓映射 / 定原点防撞 / 智能调平 / 开始雕刻）。以哪个为准？若改回 5 步需调整向导。

## 三、需要嵌入式接入的全部接口点

> 报文细节（JSON 帧 / MQTT topic / REST 路径）见 `docs/PROTOCOL.md` §2–§3。这里只列"有哪些、参数是什么、谁发谁收"。

### 3.1 HardwareService —— App ↔ ESP32（全部命令 + 广播）

**出站命令（App → 固件）**

| 方法                                                        | 参数                                              | 含义                     | 备注                                   |
| --------------------------------------------------------- | ----------------------------------------------- | ---------------------- | ------------------------------------ |
| `jog(axis, distMm)`                                       | axis∈`x/y/z`，dist 带正负                           | 点动                     | 控制台步长固定 1mm；向导 Step4 步长 0.1/1/10mm   |
| `home()`                                                  | —                                               | 回机械原点 `$H`             | —                                    |
| `setWorkZero(x,y,z)`                                      | 默认 0,0,0                                        | 写 G54 工件零点             | —                                    |
| `startSpindle(rpm)` / `stopSpindle()`                     | rpm 0–24000（UI 滑块 divisions 24，默认 12000）        | 主轴启停 `M3 Sxx`/`M5`     | —                                    |
| `setAux(key, on)`                                         | `key`∈`light`(照明)/`laser`(红点激光)/`timelapse`(延时) | 辅助输出开关                 | 自定义 `$`/M-code                       |
| `startJob()` / `pauseJob()` / `resumeJob()` / `stopJob()` | —                                               | 任务启/停/续                | **App 不发 G-code**，只触发 MCU 执行云端已下发的队列 |
| `updateToolMap(List<Tool>)`                               | 每槽 `{index,installed,name,material,defId}`      | 下发 ATC 刀仓映射（4 槽 T1–T4） | —                                    |
| `connect()` / `disconnect()` / `getStatus()`              | —                                               | 链路 + 拉一帧               | —                                    |
| `getWorkArea()`                                           | 返回 `(widthMm,heightMm)`                         | 机床行程                   | Mock 返回 Smart 3020 = **300×200mm**   |

**入站广播（固件 → App，SSOT，`statusStream` ≈5–10Hz）**

`MachineStatus` 字段（与 `lib/models/machine_status.dart` 一致）：  
`state`(idle/homing/busy/paused/alarm/disconnected) · `position`(G54) · `machinePosition` · `spindleRpm` · `feedRate` · `progress`(0–1) · `eta`(秒) · `message` · （可选 `aux` 三开关 / `tools` 4 槽）。

> ⚠️ **待确认②**：`feedRate` 已在模型和协议里，但 Mock 从不赋值 → 固件需**真实上报**当前进给。`alarm` 状态如何产生/清除也要固件定义。

### 3.2 网络与门禁

- `NetworkProbe.probe(host, port)`：TCP 2s 超时探测，判断手机与控制器是否同局域网。
- `isLocalLANProvider`：同 Wi-Fi → `true` 全功能；公网 → `false` 监视模式（UI 自动锁 Jog/开切）。
- 开发期 App 顶部有按钮可手动切换 `isLocalLAN` 测试。

> ⚠️ **待确认③（嵌入式定）**：控制器默认 IP/端口（PROTOCOL.md 暂定 TCP `8899`）、配网方式（手机如何发现设备）、LAN↔WAN 切换如何重连、是否需要鉴权。

### 3.3 摄像头 / 实时监控（RTSP）

- 组件 `lib/features/preview/rtsp_preview_widget.dart` 已写好（基于 `flutter_vlc_player`）。
- **重要澄清（2026-08-04 晚）**：这是**固定在机器侧面、看内部雕刻过程的监控头**，**不做**对位网格 / 十字准星 / 加工范围框，是纯裸画面（代码注释与实现均已确认）。早一版文档里写的"带叠加层"是误记，以代码为准。
- **当前状态：未接入构建**——`flutter_vlc_player` 还没加进 `pubspec.yaml`，控制台顶部现在只放了一个占位图标（`Icons.videocam`），没有真视频流。组件自带 `camera_discovery.dart`（自动发现局域网摄像头）+ `INTEGRATION.md` 说明如何接线。
- 入参：`rtspUrl`（如 `rtsp://admin:abc123456@192.168.1.47:554/live/ch00_0`）、`autoDiscover`、`onTap`。
- **2D 刀路预览是另一回事**：实时监控页 `JobMonitorPage` 里画的是「2D 刀路模拟进度预览」（极简矢量，由云端 TaskMetadata 而来，不是摄像头画面）。摄像头画面只在控制台顶部，二者职责分开。

> ⚠️ **待确认④（已大部分明确）**：摄像头硬件即用户已接好的那台（IPCAM，IP `192.168.1.47`，WiFi `Lunyee-YY`，密码 `abc123456`）。Rest 是 RTSP URL 实测（见第八节候选）+ App 侧接 `flutter_vlc_player`。`showOverlay` 不需要（侧面视角）。

### 4.3 智能调平 `WizardPage` Step5

**数据链路（2026-08-04 晚确认）：**
```
云端解析 G-code → 提取模型尺寸 (widthMm/heightMm) → 写入 TaskMetadata
App Step5 取出真实尺寸 → 按所选模式(0/1/2) 算出探测点阵 cols×rows
客户确认模式 → App 点「下一步」时调 setLevelingPlan(mode,cols,rows) 下发机器
机器收到点数方案 → 执行真实网格探测（App 以固件广播结果为准）
```

- 模式 0/1/2 = 不调平 / 标准（约 5cm 间距）/ 精细（约 3cm 间距）。
- 探测点数完全由**云端下发的真实图纸尺寸**决定：`cols=max(2,(宽cm/间隔).ceil())`、`rows=max(2,(高cm/间隔).ceil())`，不再写死演示面积。
- **已修复（App 侧）**：Step5 文案原来写死「标准 9 点 / 精细 12 点」且用假面积 `14.5×9.5cm`，现已改为读取 `_task.widthMm/heightMm` 实时计算并展示「`cols × rows`（共 X 点）」；新增 `HardwareService.setLevelingPlan(...)` 命令，离开调平步时把点数方案下发给机器。最终以固件真实探测网格为准。

### 4.4 自检流水线阶段（`SelfCheckPage`，固件应执行的顺序）

1. 防护罩电子门磁锁止
2. 自动开启 ATC 刀仓防护盖
3. 自动装载 T{n} 号刀具（每个 requiredTool 一条）
4. 移动至刀仓固定测头对刀（Z-Offset）
5. 关闭 ATC 刀仓防护盖
6. 运行曲面网格调平扫描
7. 主轴离心风压建立，移动至原点开切

> ⚠️ **待确认⑦（关键）**：现在 App 用定时器**假跑**自检进度（每阶段 700ms），跑完调 `startJob()`。真机应**由固件执行自检并广播阶段进度**，App 只监听渲染。需要明确：自检流水线**谁拥有**（固件驱动 vs App 驱动）？ATC「自动装载 Tn」「对刀」是固件执行还是 App 指挥？

### 关于②的详细分析：自检、ATC、对刀该归谁？

**结论：只要涉及刀具、主轴、三轴运动、测头接触的序列，都必须由固件（下位机）拥有并执行。App 只发高级意图，然后监听进度。**

理由：
1. **安全闭环必须在 MCU 内部完成**。ATC 换刀、对刀、调平扫描过程中如果网络抖动或 App 被杀，机器不能停在半空中夹持刀。固件执行才能本地处理急停、门磁、限位、报警。
2. **三端同步更简单**。机身屏、App、网页端都订阅同一份 `statusStream`，看到同样的阶段文字和进度；如果 App 驱动，机身屏和网页还得另写一套驱动。
3. **主流 CNC/3D 打印机方案都是这样**：上位机（App/网页）只发 "Start Job"，下位机运行自己的状态机，实时广播 `busy/probing/homing/leveling/running/paused/alarm`。

建议的权责划分：

| 动作 | App 侧 | 固件侧 |
| ---- | ------ | ------ |
| 用户点"开始雕刻" | 发 `startJob(taskId)` | 收到后启动内部状态机 |
| 自检 7 阶段 | 监听 `selfCheckStage` 字段渲染进度条 | 顺序执行：锁门→开盖→换刀→对刀→关盖→调平→开切，每阶段广播 |
| ATC 换刀 | 提前下发 `updateToolMap`（告诉固件 T1–T4 放的是什么刀） | 按工序自动计算该换哪把，驱动刀库电机 |
| 对刀/调平 | 发模式参数（如 `levelingMode=standard/fine`） | 执行探测，回传网格/补偿表 |
| 暂停/停止 | 发 `pauseJob()` / `stopJob()` | 立即安全减速、抬刀、停主轴 |

所以：**App 是导演，固件是演员**。App 说"开始这场戏"，固件自己按剧本演，演到哪一步实时报幕。

### 关于③的详细分析：传输协议到底怎么选？

先画清楚你想要的**数据流**：

```
局域网内（App 和 机器 同 WiFi）:
App ──选模型/点雕刻──▶ 云端
云端 ──返回 TaskMetadata + 推送 G-code ──▶ 机器（MCU）
App ──startJob()/jog/暂停/停止──▶ 机器（或经云端中转）
机器 ──statusStream──▶ App + 云端 + 机身屏

公网/4G（App 不在同 WiFi）:
App ──只监视──▶ 云端
云端 ──推送 G-code / 转发控制──▶ 机器
机器 ──statusStream──▶ 云端──▶ App
```

你想要的效果是：**App 不下发 G-code，只下发"需求和参数"，机器自己去云端取 G-code，然后自己算零点/调平/换刀**。这个逻辑完全成立，但得靠协议落地。

**两种协议对比：**

| 维度 | 裸 TCP/Telnet 直连 Grbl | MQTT（经由云/本地 Broker） |
| ---- | ---------------------- | -------------------------- |
| 复杂度 | 低，直接 socket 发 Grbl 指令 | 中，需部署/租用 Broker |
| WAN/远程 | 难，NAT 穿透麻烦 | 易，机器和 App 都连公网 Broker |
| 局域网延迟 | 极低（Jog 手感好） | 稍高（经云端多一跳） |
| 多客户端同步 | 难，App/网页/机身屏各连各 | 易，全部订阅同一 topic |
| 离线局域网 | 可以，只要机器和 App 同 WiFi | 如果 Broker 在云端，断外网失效 |
| 安全性 | 靠 WiFi 隔离，弱 | TLS + 用户名密码/Token，强 |

**我的建议：混合架构（最主流、最稳妥）**

1. **MQTT 作为“主链路”**：机器和 App 都连接到云端 MQTT Broker（或局域网内的边缘 Broker）。用于：
   - 云端给机器下任务、推 G-code 分片
   - 机器广播 `statusStream`
   - App 在公网时远程监视/暂停/停止
2. **直接 TCP 作为“局域网低延迟增强链路”**：当 App 检测到和机器同 WiFi 时，直接连机器的 TCP 端口（如 8899）。用于：
   - Jog 点动（手感好、延迟低）
   - 回零、设零、主轴开关
   - 局域网内 startJob（可优先走本地，MQTT 作为备用）

这样你既有**远程能力**（出门在外看机器），又有**本地操控的实时性**（在机器旁边点 Jog）。

**但需要嵌入式同事拍板：**
- ESP32 上同时跑 MQTT + TCP Server，资源是否够？（通常够）
- 两个链路的命令优先级/互斥怎么定？建议：本地 TCP 命令优先，MQTT 命令排队或覆盖；或者统一由固件内部队列处理。

### 关于④的通俗解释：状态字段映射是什么？

Grbl 会周期性吐这种实时报告：
```
<Idle|MPos:10.000,20.000,0.000|FS:12000,1500|WCO:0.000,0.000,0.000>
```
意思是：状态空闲、机器坐标 (10,20,0)、主轴 12000rpm、进给 1500mm/min、工件偏置 (0,0,0)。

固件要做的事就是：**每收到这样一帧，解析后转成 App 认识的 JSON**：
```json
{
  "state": "idle",
  "position": {"x":10,"y":20,"z":0},
  "machinePosition": {"x":10,"y":20,"z":0},
  "spindleRpm": 12000,
  "feedRate": 1500
}
```
然后每秒 5–10 次广播给 App。

**所以问题④其实是确认**：Grbl 实时报告里的每个字段，固件都能正确翻译并上传吗？特别是 `feedRate`（进给速度）和 `alarm`（报警码），目前 Mock 没给真实值。

### 关于⑦的详细分析：材质参数表放云端还是各端各一份？

你提的两种模式：

| 模式 | 优点 | 缺点 |
| ---- | ---- | ---- |
| A. 云端统一参数表，各界面共用 | 一改全改；多客户端一致；云端可按用户/机型/固件版本灵活下发 | 离线时看不到最新；需要网络同步 |
| B. 每端各存一份 | 离线可用；不依赖网络 | 多处维护，容易不一致；更新麻烦 |

**我的建议：A + 本地缓存 = 最佳方案**

- **云端为主表**：材料库、rpm/feed/plunge、推荐刀具、说明文字都放在云端。机身屏、App、网页端都从云端拉。
- **本地缓存**：App 启动时拉一次，没网时用上次缓存。机身屏同理。
- **自动刷新**：用户打开材质选择页时静默刷新；云端更新后下次进入即生效。
- **版本号机制**：给参数表一个 `version`，本地缓存带版本，避免每次都全量拉。

这样既能保证**三端一致**，又能**离线可用**，以后云端想新增材料或调整参数也不需要发 App 新版。

**落地方案**：
- 云端新增接口 `GET /api/v1/materials` 返回参数表 JSON。
- App 本地 `material_db.dart` 改为"先读缓存 → 异步刷新 → 写入缓存"。
- 机身屏、网页端也调用同一接口。

### 关于⑩：网络、配网、鉴权推荐方案

目标是：**用户基本无感，但安全可控**。

#### 1. IP 与端口
- **不要写死 IP**：机器用 DHCP 自动获取 IP（你家路由器会分配，比如现在的 `192.168.1.47`）。
- **固定端口**：机器 TCP 服务固定 `8899`，MQTT 固定 `1883`（TLS 用 `8883`）。

#### 2. 设备发现（App 怎么找到机器）
- **推荐 mDNS/Bonjour**：机器启动后在局域网广播 `_alexcnc._tcp.local`，App 扫描即可列出"客厅雕刻机"、"工作室雕刻机"，用户点一下就连上。
- **备选：手动输入 IP**：在"我的 → 设备管理"里输入 IP 地址，适合调试或 mDNS 被路由器屏蔽的场景。

#### 3. 首次配网（机器怎么连上你家 WiFi）
- **推荐 AP 配网模式**：
  1. 机器首次上电发出一个 WiFi 热点，比如 `alexcnc-XXXX`。
  2. 手机连这个热点，App 弹窗让用户选择家里 WiFi 并输入密码。
  3. 机器收到 SSID/密码后切换去连家里 WiFi，App 自动切回家用 WiFi 重新发现机器。
- 这是扫地机器人/智能音箱的主流做法，用户友好。

#### 4. LAN↔WAN 切换与重连
- **判断逻辑**：App 比较"手机当前 WiFi 名称"和"机器保存的 WiFi 名称"是否相同，且 mDNS 能扫到机器 → 同局域网。
- 扫不到 → 走云端 MQTT（WAN 监视模式）。
- 机器断网重连后自动重连 MQTT；App 断网重连后自动恢复订阅。

#### 5. 鉴权
- **推荐 Token 鉴权**：
  - 每台机器出厂内置唯一设备 Token（类似序列号 + 密钥）。
  - 首次配对时 App 扫描到机器，双方交换 Token 并绑定到用户账号。
  - 以后每次连接（本地 TCP 或 MQTT）都携带 Token，防止邻居误连你的机器。
- **本地 TCP 可再加一层简单 PIN**：首次配对时机器屏幕/App 显示 6 位配对码，确认后才绑定，像蓝牙配对。

### 9.2 ③ 协议深度分析：MQTT Broker 用云端还是本地边缘？ESP32 能否同时跑 MQTT + TCP？

**结论：主链路用「云端 MQTT Broker」，局域网低延迟控制用「ESP32 本地 TCP」做增强。ESP32 完全能同时跑 MQTT Client + TCP Server。**

#### A. MQTT Broker 放哪？

| 方案 | 优点 | 缺点 | 结论 |
| ---- | ---- | ---- | ---- |
| **云端 Broker（推荐）** | 出厂即可用；WAN/远程天然打通；App 和机器都连它，多客户端自动同步；无需用户在局域网搭服务器 | 局域网断外网时无法经云控制（但本地 TCP 兜底）；依赖云稳定性 | ✅ 主选 |
| 本地边缘 Broker（机器或网关上跑） | 局域网零延迟、断外网也能用 | ESP32 跑 Broker 不堪重负（内存/连接数）；多机器需独立 Broker；远程访问要穿透 | ❌ 不推荐由机器担任 Broker |

**所以**：在云端部署一个 MQTT Broker（EMQX / Mosquitto / 云服务），机器是 **MQTT Client**，App 也是 **MQTT Client**（手机联网即可）。这是贯穿 LAN+WAN 的统一 backbone。

#### B. ESP32 同时跑 MQTT + TCP 是否 OK？

**完全 OK，这是非常成熟的组合。** 原因：

- ESP32（ESP32-WROOM / S3）是**双核**，`WiFi` 协议栈在底层已独立线程，应用层跑 MQTT Client（连接云端）+ AsyncTCP Server（监听本地 8899）互不阻塞。
- 内存：ESP32 通常有 320KB+ 可用 RAM，MQTT 客户端 + 一个轻量 TCP Server + Grbl 解析 + 状态机，占用可控。
- 业界大量项目（3D 打印机、CNC、机器人）都是 ESP32 同时做"连云 + 局域直连"。

**推荐固件层分工**：
- 一个任务解析 Grbl 实时报告（`$` 状态机），维护 `MachineStatus` 真值。
- 一个 MQTT 任务：订阅云端主题（命令/G-code 分片），发布 `statusStream`。
- 一个 TCP Server 任务：给局域网 App 提供低延迟直连（Jog/回零/设零/主轴/startJob）。
- 一个本地命令队列：本地 TCP 命令与 MQTT 命令都汇入同一队列，由状态机串行执行，**避免两条链路打架**（建议：本地 TCP 命令优先级略高，或同 task 内互斥）。

#### C. 数据流（最终形态）

```
【局域网内 · 手机同 WiFi】
App ──Jog/回零/设零/主轴──▶ ESP32 TCP:8899（本地直连，低延迟）
App ──startJob()/暂停/停止──▶ ESP32 TCP:8899 或 云端MQTT（二者皆可）
App ◀──statusStream── ESP32（本地直连或经云端）

【公网/远程】
App ──仅监视+暂停/停止──▶ 云端 MQTT ──▶ ESP32
ESP32 ──statusStream──▶ 云端 MQTT ──▶ App（延迟略高但远程可用）

【任务下发】
云端 ──解析 G-code 直推 G-code 分片──▶ ESP32（MQTT 或 LAN 直传）
App 只取 TaskMetadata + 极简 2D 矢量，不发 G-code
```
